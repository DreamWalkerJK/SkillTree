# SHA-256：标准流程、压缩函数、安全性质与工程实践

SHA-256（Secure Hash Algorithm 256-bit）是 SHA-2 家族中的密码学哈希算法，由 NIST 的 FIPS 180-4《Secure Hash Standard》规定。它把长度小于 $2^{64}$ bit 的消息映射为固定的 256 bit 摘要，内部按 512 bit 分组、32 bit 字和 64 轮压缩运算处理数据 \[1\]。

SHA-256 是**确定性的无密钥哈希函数**：相同字节串总是产生相同摘要。它适合内容指纹、完整性校验、数字签名协议中的摘要步骤以及 HMAC-SHA-256 的底层哈希，但它不是加密算法、消息认证码或口令哈希函数。NIST 目前仍批准 SHA-2 家族用于安全哈希应用，并指出没有仅因 SHA-3 发布而全面迁移出 SHA-2 的必要 \[2\]\[13\]。

> **标准状态：** 本文以当前发布的 FIPS 180-4 Update 1 为规范基线。NIST 于 2023 年宣布将修订 FIPS 180-4；在新版本正式取代它之前，工程实现仍应以当前有效出版物、所用协议和合规要求为准 \[1\]\[14\]。
>
> **核心边界：** 256 bit 输出不等于“所有目标都有 256 bit 安全强度”。在理想模型下，SHA-256 的经典通用碰撞强度约为 128 bit，原像强度约为 256 bit；裸 SHA-256 不能证明消息来自可信发送方，也不应直接用于存储口令。

## 1. 标准定位与算法参数

### 1.1 SHA-2 家族中的 SHA-256

FIPS 180-4 规定了 SHA-1 以及 SHA-2 家族的 SHA-224、SHA-256、SHA-384、SHA-512、SHA-512/224 和 SHA-512/256。SHA-256 与 SHA-224 使用相同的 512 bit 分组和 32 bit 字级运算，但初始值和输出规则不同；SHA-384、SHA-512 及 SHA-512 的截断变体使用 1024 bit 分组和 64 bit 字级运算 \[1\]。

名称中的“256”只表示摘要长度，不表示分组长度、内部轮数或所有安全目标的工作量。

| 参数 | SHA-256 取值 | 含义 |
| --- | ---: | --- |
| 摘要长度 | 256 bit（32 byte） | 最终输出由 8 个 32 bit 状态字连接而成 |
| 消息分组长度 | 512 bit（64 byte） | 每次压缩函数处理一个分组 |
| 字长 | 32 bit | 位运算和模加法的基本单位 |
| 消息调度字 | 64 个 | 每个分组由 16 个原始字扩展为 64 个字 |
| 压缩轮数 | 64 轮 | 每轮消费一个调度字和一个轮常量 |
| 链式状态 | 256 bit | 8 个 32 bit 状态字 |
| 长度字段 | 64 bit | 记录填充前消息的 bit 长度 |
| 标准消息长度上限 | $\ell<2^{64}$ bit | 由 64 bit 长度字段和标准定义共同限定 |
| 字节序 | 大端序 | 分组解析、长度字段与摘要序列化均按大端顺序 |

### 1.2 输入、输出与符号

形式上，可把 SHA-256 写为

$$
\operatorname{SHA256}:\{0,1\}^{<2^{64}}\rightarrow\{0,1\}^{256}.
$$

标准定义处理 bit 串；Python、.NET 等常用 API 通常接收字节串。因此，应用层必须先明确文本编码、序列化格式和规范化规则，再把确定的字节序列交给 SHA-256。字符串“密码学”的 UTF-8、UTF-16LE 与其他编码具有不同字节表示，摘要自然也不同。

本文使用以下符号：

| 符号 | 含义 |
| --- | --- |
| $x\oplus y$ | 按位异或 |
| $x\land y$ | 按位与 |
| $\neg x$ | 在 32 bit 字范围内按位取反 |
| $x+y$ | 除非另有说明，均表示模 $2^{32}$ 加法 |
| $\operatorname{ROTR}^n(x)$ | 32 bit 字循环右移 $n$ 位 |
| $\operatorname{SHR}^n(x)$ | 32 bit 字逻辑右移 $n$ 位，高位补零 |
| $X\mathbin\Vert Y$ | bit 串或字节串连接 |
| $H_i^{(j)}$ | 处理完第 $j$ 个消息分组后的第 $i$ 个状态字 |

循环右移与逻辑右移不能互换：

$$
\operatorname{ROTR}^n(x)
=(x\gg n)\lor(x\ll(32-n))
\pmod{2^{32}},
$$

而 $\operatorname{SHR}^n(x)=x\gg n$ 会丢弃移出的低位。

### 1.3 哈希函数不提供什么

- **不可逆不是数学上的单射。** 输入空间远大于 256 bit 输出空间，碰撞必然存在；“不可逆”是针对资源受限攻击者的计算困难性表述。
- **摘要不是密文。** SHA-256 没有解密密钥，也不能恢复原消息。
- **裸摘要不认证发送者。** 攻击者若能同时替换文件和摘要，就能重新计算一个匹配的新摘要。
- **快速并非口令存储优点。** SHA-256 可被 CPU、GPU 和专用硬件高速计算，不能单独抵御低熵口令猜测。

## 2. 数据表示、填充与消息分组

SHA-256 是迭代式构造。高层数据流为：

```text
原始消息 M
  -> 追加 1 bit、若干 0 bit 和 64 bit 原始长度
  -> 切分为 N 个 512 bit 分组 M^(1) ... M^(N)
  -> 每个分组解析为 16 个大端 32 bit 字
  -> 扩展为 64 个消息调度字 W[0] ... W[63]
  -> 64 轮压缩并前馈到链式状态
  -> 连接最终 8 个状态字，得到 256 bit 摘要
```

### 2.1 填充规则

设原始消息长度为 $\ell$ bit，且 $\ell<2^{64}$。先追加一个 `1` bit，再追加最少数量的 `0` bit，使长度达到 448 modulo 512。令 $k$ 为所需零 bit 数，则

$$
\ell+1+k\equiv448\pmod{512},
\qquad k\ge0.
$$

最后追加 $\ell$ 的 64 bit 大端无符号表示 $[\ell]_{64}$：

$$
M'
=M\mathbin\Vert1\mathbin\Vert0^k\mathbin\Vert[\ell]_{64}.
$$

因此

$$
|M'|=\ell+1+k+64\equiv0\pmod{512}.
$$

这里的长度字段记录的是**填充前**的消息长度，而不是追加 `1`、零 bit 或长度字段之后的长度。

填充有两个容易忽略的边界：

1. 即使原消息长度已经是 512 bit 的整数倍，也必须追加填充；此时会新增一个完整的填充分组。
2. 对字节对齐的 API，长度为 55 byte 的消息还可在当前分组容纳 `0x80` 和 8 byte 长度字段；长度为 56 byte 时则必须再增加一个分组。

### 2.2 分组与大端解析

填充后的消息被切分为 $N$ 个 512 bit 分组：

$$
M'=M^{(1)}\mathbin\Vert M^{(2)}
\mathbin\Vert\cdots\mathbin\Vert M^{(N)}.
$$

每个分组再按大端序解析为 16 个 32 bit 字：

$$
M^{(i)}=M_0^{(i)}\mathbin\Vert M_1^{(i)}
\mathbin\Vert\cdots\mathbin\Vert M_{15}^{(i)}.
$$

例如 4 个字节 `61 62 63 80` 被解释为 32 bit 字 `0x61626380`，而不是宿主机本地端序下的 `0x80636261`。

## 3. 逻辑函数、初始值与轮常量

### 3.1 选择函数与多数函数

SHA-256 的两个三输入逻辑函数为

$$
\operatorname{Ch}(x,y,z)
=(x\land y)\oplus(\neg x\land z),
$$

$$
\operatorname{Maj}(x,y,z)
=(x\land y)\oplus(x\land z)\oplus(y\land z).
$$

逐 bit 理解时：

- $\operatorname{Ch}$ 在 $x=1$ 时选择 $y$，在 $x=0$ 时选择 $z$；
- $\operatorname{Maj}$ 输出 $x,y,z$ 三个对应 bit 中的多数值。

### 3.2 大写与小写 Sigma 函数

压缩轮使用大写 Sigma：

$$
\begin{aligned}
\Sigma_0(x)
&=\operatorname{ROTR}^{2}(x)
\oplus\operatorname{ROTR}^{13}(x)
\oplus\operatorname{ROTR}^{22}(x),\\
\Sigma_1(x)
&=\operatorname{ROTR}^{6}(x)
\oplus\operatorname{ROTR}^{11}(x)
\oplus\operatorname{ROTR}^{25}(x).
\end{aligned}
$$

消息调度使用小写 sigma：

$$
\begin{aligned}
\sigma_0(x)
&=\operatorname{ROTR}^{7}(x)
\oplus\operatorname{ROTR}^{18}(x)
\oplus\operatorname{SHR}^{3}(x),\\
\sigma_1(x)
&=\operatorname{ROTR}^{17}(x)
\oplus\operatorname{ROTR}^{19}(x)
\oplus\operatorname{SHR}^{10}(x).
\end{aligned}
$$

小写函数的最后一项是逻辑右移，不是循环右移。大小写 Sigma 的旋转距离也完全不同。

### 3.3 初始哈希值

处理第一个消息分组前，8 个状态字初始化为：

| 状态字 | 十六进制值 |
| --- | --- |
| $H_0^{(0)}$ | `6a09e667` |
| $H_1^{(0)}$ | `bb67ae85` |
| $H_2^{(0)}$ | `3c6ef372` |
| $H_3^{(0)}$ | `a54ff53a` |
| $H_4^{(0)}$ | `510e527f` |
| $H_5^{(0)}$ | `9b05688c` |
| $H_6^{(0)}$ | `1f83d9ab` |
| $H_7^{(0)}$ | `5be0cd19` |

它们来自前 8 个素数平方根小数部分的前 32 bit。64 个轮常量 $K_0,\ldots,K_{63}$ 则来自前 64 个素数立方根小数部分的前 32 bit \[1\]。这些值是公开的、可复算的标准参数，不是密钥，也不应被应用程序替换。

## 4. 消息调度与 64 轮压缩

### 4.1 消息调度

对每个 512 bit 分组，构造 $W_0,\ldots,W_{63}$。前 16 个字直接来自当前分组：

$$
W_t=M_t^{(i)},\qquad0\le t\le15.
$$

其余字递推为

$$
W_t
=\sigma_1(W_{t-2})
+W_{t-7}
+\sigma_0(W_{t-15})
+W_{t-16}
\pmod{2^{32}},
\qquad16\le t\le63.
$$

调度扩展让后续轮同时依赖当前分组中相距较远的多个位置。它不是把 512 bit 信息扩展成更多独立熵，而是为压缩函数生成确定性的 64 轮输入。

### 4.2 工作变量与轮函数

处理第 $i$ 个分组前，把当前链式状态复制到工作变量：

$$
(a,b,c,d,e,f,g,h)
=\left(
H_0^{(i-1)},H_1^{(i-1)},\ldots,H_7^{(i-1)}
\right).
$$

第 $t$ 轮计算

$$
T_1
=h+\Sigma_1(e)+\operatorname{Ch}(e,f,g)+K_t+W_t
\pmod{2^{32}},
$$

$$
T_2
=\Sigma_0(a)+\operatorname{Maj}(a,b,c)
\pmod{2^{32}}.
$$

然后同步更新：

$$
\begin{aligned}
h&\leftarrow g,\\
g&\leftarrow f,\\
f&\leftarrow e,\\
e&\leftarrow d+T_1,\\
d&\leftarrow c,\\
c&\leftarrow b,\\
b&\leftarrow a,\\
a&\leftarrow T_1+T_2,
\end{aligned}
\qquad\pmod{2^{32}}.
$$

“同步更新”意味着右侧全部读取本轮开始时的旧值。若在命令式实现中依次覆盖 `a` 到 `h`，后续赋值可能错误地读到本轮新值。

### 4.3 分组前馈与最终输出

64 轮结束后，把工作变量逐字加回原链式状态：

$$
\begin{aligned}
H_0^{(i)}&=H_0^{(i-1)}+a, &
H_1^{(i)}&=H_1^{(i-1)}+b,\\
H_2^{(i)}&=H_2^{(i-1)}+c, &
H_3^{(i)}&=H_3^{(i-1)}+d,\\
H_4^{(i)}&=H_4^{(i-1)}+e, &
H_5^{(i)}&=H_5^{(i-1)}+f,\\
H_6^{(i)}&=H_6^{(i-1)}+g, &
H_7^{(i)}&=H_7^{(i-1)}+h,
\end{aligned}
\qquad\pmod{2^{32}}.
$$

这个前馈步骤必须在**每个**消息分组之后执行。处理完最后一个分组后，按大端顺序连接 8 个状态字：

$$
\operatorname{SHA256}(M)
=H_0^{(N)}\mathbin\Vert H_1^{(N)}
\mathbin\Vert\cdots\mathbin\Vert H_7^{(N)}.
$$

原始摘要是 32 byte。常见的 64 字符十六进制字符串只是编码表示，因为每个字节写成两个十六进制字符。

## 5. `abc` 的完整计算脉络

ASCII 字符串 `abc` 对应字节

```text
61 62 63
```

原始长度 $\ell=24$ bit。填充方程给出

$$
24+1+k\equiv448\pmod{512},
$$

所以 $k=423$。唯一的填充分组为：

```text
61626380 00000000 00000000 00000000
00000000 00000000 00000000 00000000
00000000 00000000 00000000 00000000
00000000 00000000 00000000 00000018
```

因此：

```text
W[ 0] = 0x61626380
W[ 1] ... W[14] = 0x00000000
W[15] = 0x00000018
```

递推得到的前几个扩展字为：

```text
W[16] = 0x61626380
W[17] = 0x000f0000
W[18] = 0x7da86405
W[19] = 0x600003c6
W[20] = 0x3e9d7b78
W[21] = 0x0183fc00
W[22] = 0x12dcbfdb
W[23] = 0xe2e2c38e
```

第 64 轮结束、尚未执行分组前馈时：

```text
a = 0x506e3058    b = 0xd39a2165
c = 0x04d24d6c    d = 0xb85e2ce9
e = 0x5ef50f24    f = 0xfb121210
g = 0x948d25b6    h = 0x961f4894
```

把这些值分别加回初始状态后：

```text
H[0] = 0xba7816bf    H[1] = 0x8f01cfea
H[2] = 0x414140de    H[3] = 0x5dae2223
H[4] = 0xb00361a3    H[5] = 0x96177a9c
H[6] = 0xb410ff61    H[7] = 0xf20015ad
```

按大端顺序连接即为：

```text
ba7816bf8f01cfea414140de5dae2223
b00361a396177a9cb410ff61f20015ad
```

该结果与 NIST 示例和 RFC 6234 测试材料一致 \[3\]\[4\]。

## 6. Python 标准库工程示例

生产代码应优先使用平台密码学库，而不是自行实现压缩函数。Python 的 `hashlib.sha256` 接收字节类对象，并支持一次性或增量计算 \[7\]。

本文 Python 示例以 Python 3.10 或更高版本为运行基线；代码使用了 PEP 604 联合类型语法（如 `bytes | bytearray`）和 `int.bit_count()`。在更早版本上运行时，需要相应改写类型注解和位计数逻辑。

### 6.1 字节串、文本与文件

```python
from __future__ import annotations

import hashlib
from pathlib import Path


def sha256_bytes(data: bytes) -> bytes:
    """返回 32 字节 SHA-256 摘要。"""
    return hashlib.sha256(data).digest()


def sha256_text(text: str) -> str:
    """按明确的 UTF-8 编码计算 64 字符小写十六进制摘要。"""
    return hashlib.sha256(text.encode("utf-8")).hexdigest()


def sha256_file(path: Path, chunk_size: int = 1024 * 1024) -> str:
    """流式计算文件摘要，内存占用与文件大小无关。"""
    if chunk_size <= 0:
        raise ValueError("chunk_size must be positive")

    hasher = hashlib.sha256()
    with path.open("rb") as stream:
        while chunk := stream.read(chunk_size):
            hasher.update(chunk)
    return hasher.hexdigest()


if __name__ == "__main__":
    print(sha256_text("abc"))
    print(sha256_bytes(b"abc").hex())
```

输出均为：

```text
ba7816bf8f01cfea414140de5dae2223b00361a396177a9cb410ff61f20015ad
```

增量调用满足

```python
import hashlib


hasher = hashlib.sha256()
hasher.update(b"ab")
hasher.update(b"c")

assert hasher.digest() == hashlib.sha256(b"abc").digest()
```

也就是说，`update(x)` 后再 `update(y)` 等价于对 `x + y` 的字节连接求哈希；分块边界不会进入摘要语义。

### 6.2 摘要比较

普通文件校验通常可直接比较摘要字节。若比较结果参与认证决策，应使用常量时间比较函数，避免把提前返回的比较时序暴露给攻击者：

```python
import hmac


def digest_matches(actual: bytes, expected: bytes) -> bool:
    if len(actual) != 32 or len(expected) != 32:
        return False
    return hmac.compare_digest(actual, expected)
```

常量时间比较不能弥补错误的安全构造：若 `expected` 本身来自不可信来源，比较方式再安全也不能建立真实性。

## 7. Python 教学性完整实现

以下实现直接表达 FIPS 180-4 的填充、消息调度、64 轮压缩和前馈规则。它用于理解规范与交叉验证，不适合生产环境：它会复制并完整填充消息，不支持流式处理，也没有标准库实现所具有的优化、平台集成和长期审计。

```python

MASK32 = 0xFFFFFFFF

INITIAL_HASH = (

    0x983E5152, 0xA831C66D, 0xB00327C8, 0xBF597FC7,
    0xC6E00BF3, 0xD5A79147, 0x06CA6351, 0x14292967,
    0x27B70A85, 0x2E1B2138, 0x4D2C6DFC, 0x53380D13,

    0xA2BFE8A1, 0xA81A664B, 0xC24B8B70, 0xC76C51A3,
    0xD192E819, 0xD6990624, 0xF40E3585, 0x106AA070,
    0x19A4C116, 0x1E376C08, 0x2748774C, 0x34B0BCB5,
    0x391C0CB3, 0x4ED8AA4A, 0x5B9CCA4F, 0x682E6FF3,

    0x90BEFFFA, 0xA4506CEB, 0xBEF9A3F7, 0xC67178F2,

def rotate_right(value: int, count: int) -> int:
    return (
        (value >> count) | (value << (32 - count))
    ) & MASK32


def sha256(data: bytes | bytearray | memoryview) -> bytes:
    """
    返回 32 字节 SHA-256 摘要。

    教学实现：算法主体不调用 hashlib。
    """
    if not isinstance(data, (bytes, bytearray, memoryview)):
        raise TypeError("data must be a bytes-like object")

    message = bytearray(data)
    original_bit_length = len(message) * 8

    if original_bit_length >= (1 << 64):
        raise ValueError("message is too long for SHA-256")

    message.append(0x80)
    message.extend(b"\x00" * ((56 - len(message)) % 64))
    message.extend(original_bit_length.to_bytes(8, byteorder="big"))

    state = list(INITIAL_HASH)

    for block_offset in range(0, len(message), 64):
        block = message[block_offset:block_offset + 64]
        schedule = [
            int.from_bytes(block[i:i + 4], byteorder="big")
            for i in range(0, 64, 4)
        ]

        for t in range(16, 64):
            sigma0 = (
                rotate_right(schedule[t - 15], 7)
                ^ rotate_right(schedule[t - 15], 18)
                ^ (schedule[t - 15] >> 3)
            )
            sigma1 = (
                rotate_right(schedule[t - 2], 17)
                ^ rotate_right(schedule[t - 2], 19)
                ^ (schedule[t - 2] >> 10)
            )
            schedule.append(
                (
                    schedule[t - 16]
                    + sigma0
                    + schedule[t - 7]
                    + sigma1
                ) & MASK32
            )

        a, b, c, d, e, f, g, h = state

        for t in range(64):
            upper_sigma1 = (
                rotate_right(e, 6)
                ^ rotate_right(e, 11)
                ^ rotate_right(e, 25)
            )
            choose = (e & f) ^ ((~e & MASK32) & g)
            temp1 = (
                h
                + upper_sigma1
                + choose
                + ROUND_CONSTANTS[t]
                + schedule[t]
            ) & MASK32

            upper_sigma0 = (
                rotate_right(a, 2)
                ^ rotate_right(a, 13)
                ^ rotate_right(a, 22)
            )
            majority = (a & b) ^ (a & c) ^ (b & c)
            temp2 = (upper_sigma0 + majority) & MASK32

            h, g, f, e, d, c, b, a = (
                g,
                f,
                e,
                (d + temp1) & MASK32,
                c,
                b,
                a,
                (temp1 + temp2) & MASK32,
            )

        state = [
            (old + new) & MASK32
            for old, new in zip(state, (a, b, c, d, e, f, g, h))
        ]

    return b"".join(
        word.to_bytes(4, byteorder="big")
        for word in state
    )
```

Python 整数不会像固定宽度无符号整数那样自然溢出，所以实现必须在消息调度、轮临时值、工作变量和前馈加法处显式 `& 0xFFFFFFFF`。同理，Python 的 `~e` 是任意精度负整数，计算 $\operatorname{Ch}$ 时应先用 `& MASK32` 限定到 32 bit。

## 9. 安全性质与复杂度边界

### 9.1 三类目标必须区分

下表先以输出 $n=256$ bit 的理想哈希给出碰撞与原像的经典通用基线；第二原像一栏另计入 SHA-256 的 Merkle–Damgård 结构在超长消息下的已知结构性攻击：

| 安全目标 | 攻击者的任务 | SHA-256 的经典评估 |
| --- | --- | ---: |
| 碰撞抵抗 | 找到任意 $M\ne M'$ 使 $H(M)=H(M')$ | 理想通用基线约 128 bit |
| 原像抵抗 | 给定摘要 $y$，找到 $M$ 使 $H(M)=y$ | 理想通用基线约 256 bit |
| 第二原像抵抗 | 给定 $M$，找到 $M'\ne M$ 使 $H(M')=H(M)$ | 约 201–256 bit，随被攻击消息长度而变化 |

碰撞工作量来自[生日攻击](./生日攻击.md)：

$$
q\approx\sqrt{2\ln2}\,2^{n/2}
\approx1.1774\cdot2^{128}
$$

次独立求值可在理想模型下达到约 50% 的至少一次碰撞概率。这个结论不适用于给定目标摘要的原像搜索。

NIST 当前安全强度表把 SHA-256 的碰撞强度列为 128 bit、原像强度列为 256 bit；对极长 Merkle–Damgård 消息，第二原像强度会随消息分组数下降，在 SHA-256 标准允许的消息长度范围内约为 201–256 bit \[2\]\[11\]。因此，“SHA-256 只有 128 bit 安全性”和“SHA-256 有 256 bit 安全性”都必须附带具体安全目标。

### 9.2 摘要长度不是安全证明

上述数值是理想模型中的通用攻击基线和 NIST 给出的安全强度，不是仅由输出长度自动推出的算法安全证明。真实哈希函数还必须抵抗其压缩结构、消息调度和轮函数可能产生的专用密码分析。

截至本文所引用的 NIST 状态，SHA-256 仍属于批准的 SHA-2 算法，可用于安全哈希应用 \[2\]\[13\]。工程判断应以当前标准、最佳公开分析、协议要求和合规基线为准，而不能把“尚无实用攻击”误写成“数学上永不可能发生碰撞”。

### 9.3 截断会降低强度

若系统只存储或比较 SHA-256 的前 $t$ bit，则有效输出空间只有 $2^t$：

$$
\text{经典通用碰撞强度}\le\frac t2\text{ bit},
\qquad
\text{经典通用原像强度}\le t\text{ bit}.
$$

例如截断为 128 bit 时，理想碰撞强度至多约 64 bit，而不是继续保持 128 bit。截断位数必须由协议的安全目标、对象总量、攻击查询数和允许风险共同决定。

更多概率推导见[生日悖论](../Mathematics/生日悖论.md)、[生日攻击](./生日攻击.md)与[哈希碰撞](../Algorithm/哈希碰撞.md)。

### 9.4 雪崩效应不是安全证明

良好的密码学哈希应具有强扩散：输入发生很小变化时，摘要看起来会发生大范围、不可预测的变化。常见直观表述是“翻转一个输入 bit，平均约有一半输出 bit 改变”。这里的“一半”是对大量输入和 bit 位置统计后的期望，不要求每一对消息都恰好改变 128 bit。

两个等长 bit 串 $x,y$ 的汉明距离为

$$
d_H(x,y)=\operatorname{wt}(x\oplus y),
$$

其中 $\operatorname{wt}$ 表示 1 bit 的数量。下面把 `abc` 首字节 `a` 的最低有效位翻转一次：

```python
import hashlib


def hamming_distance(left: bytes, right: bytes) -> int:
    if len(left) != len(right):
        raise ValueError("inputs must have equal length")
    return sum((x ^ y).bit_count() for x, y in zip(left, right))


original = b"abc"
changed = bytes([original[0] ^ 0x01]) + original[1:]

original_digest = hashlib.sha256(original).digest()
changed_digest = hashlib.sha256(changed).digest()

print("input bit differences:", hamming_distance(original, changed))
print(
    "digest bit differences:",
    hamming_distance(original_digest, changed_digest),
    "/ 256",
)
```

确定性输出为：

```text
input bit differences: 1
digest bit differences: 112 / 256
```

这个样本改变了 112 个摘要 bit，并非恰好 128 个。雪崩测试可用于发现“输出几乎不变”“某些位置恒定”等明显实现缺陷，但少量样本具有良好雪崩外观，不能证明碰撞抵抗、原像抵抗或算法不存在结构性攻击。

### 9.5 经典强度与量子查询口径

本文前述 128 bit 碰撞强度和 256 bit 原像强度采用经典计算模型。在理想黑盒查询模型中，BHT 类量子碰撞算法与碰撞问题的量子查询下界共同给出 $\Theta(2^{n/3})$；Grover 搜索与无结构搜索的量子查询下界共同给出 $\Theta(2^{n/2})$。对 $n=256$，相应查询量级约为 $2^{85.3}$ 和 $2^{128}$ \[16\]\[17\]\[19\]\[20\]。

这些是渐近**查询复杂度**，不是现实量子计算机的运行秒数：可逆 SHA-256 电路、量子纠错、逻辑门深度、存储和并行模型都会显著影响实际资源。NIST 的经典安全强度口径也不应与量子查询指数混写为同一个结论 \[18\]。本节只量化理想黑盒中的通用碰撞和原像查询复杂度，不对超长 Merkle–Damgård 消息的量子第二原像复杂度给出统一数值。更完整的模型边界见[生日攻击：经典与量子复杂度](./生日攻击.md#9-经典与量子复杂度)。

## 10. 长度扩展、HMAC 与截断

### 10.1 Merkle–Damgård 长度扩展性质

SHA-256 的最终摘要暴露了处理完 `M || pad(M)` 后的链式状态。若攻击者知道 `SHA256(M)` 和 `M` 的长度，即使不知道 `M` 的内容，也可从该状态继续压缩附加数据 `X`，计算

$$
\operatorname{SHA256}
\left(
M\mathbin\Vert\operatorname{pad}(M)\mathbin\Vert X
\right).
$$

这不会恢复 `M`，也不会直接给出 `SHA256(M || X)`；被扩展消息中包含原消息的标准填充。只计算扩展摘要不要求知道 `M` 的内容，但若要向验证方提交完整的可验证消息，攻击者通常还需要知道或取得公开消息部分 `M`。

长度扩展足以破坏某些自制认证方案。例如

$$
\operatorname{SHA256}(K\mathbin\Vert M)
$$

若把秘密前缀 $K$ 与公开消息 $M$ 直接连接后求哈希，攻击者可猜测 $|K|$，提交

$$
M\mathbin\Vert
\operatorname{pad}(K\mathbin\Vert M)
\mathbin\Vert X
$$

并从原标签所暴露的链式状态计算相应的新标签。NIST SP 800-224 初始公开草案对 SHA-2 的长度扩展性质及 HMAC 的相关边界给出了明确说明；该文档目前仍是草案，而不是最终标准 \[15\]。

### 10.2 使用 HMAC-SHA-256 进行消息认证

HMAC 用内外两层结构封装底层哈希 \[5\]：

$$
\operatorname{HMAC}_K(M)
=H\left(
(K'\oplus\operatorname{opad})
\mathbin\Vert
H\left((K'\oplus\operatorname{ipad})\mathbin\Vert M\right)
\right),
$$

其中 SHA-256 的分组长度为 64 byte。若原密钥 $K$ 长于 64 byte，先计算 $\operatorname{SHA256}(K)$，再在右侧补零到 64 byte；否则直接把 $K$ 补零到 64 byte，所得结果即 $K'$。$\operatorname{ipad}$ 是字节 `0x36` 重复 64 次，$\operatorname{opad}$ 是字节 `0x5c` 重复 64 次。

规范状态方面，FIPS 198-1 的 NIST 出版物页面目前仍标为 Final；NIST 在 2025 年发布的是**拟撤回**该 FIPS 并把内容迁移到 SP 800-224 的征求意见通知，而不是已经完成撤回。拟承接内容的 SP 800-224 截至访问日期仍为 Initial Public Draft；RFC 2104 的状态则是 Informational RFC \[5\]\[15\]\[21\]。

HMAC-SHA-256 不应被替换为 `SHA256(key + message)`、`SHA256(message + key)` 或其他自行拼接方案。HMAC 的外层哈希使底层 SHA-256 的经典长度扩展不能直接转化为 HMAC 标签伪造 \[5\]\[15\]。

Python 示例 \[8\]：

```python
import hashlib
import hmac


def create_tag(key: bytes, message: bytes) -> bytes:
    return hmac.new(key, message, hashlib.sha256).digest()


def verify_tag(key: bytes, message: bytes, received_tag: bytes) -> bool:
    expected_tag = create_tag(key, message)
    return hmac.compare_digest(expected_tag, received_tag)
```

密钥必须来自密码学安全的随机源或协议规定的密钥派生流程，不能把低熵口令直接当作高质量 HMAC 密钥。HMAC-SHA-256 的标准测试向量可参考 RFC 4231 \[6\]。

HMAC 只证明持有共享密钥的一方生成了匹配标签，不自动提供消息新鲜性、抗重放或数字签名意义上的不可否认性。需要抗重放时，协议应把 nonce、单调序列号或受约束的时间戳纳入被认证数据，并在验证端维护去重状态、序列窗口或时效策略。

### 10.3 HMAC 标签截断

某些协议允许截断 HMAC 标签，但这属于协议级选择。采用 RFC/NIST 定义的截断 HMAC 时，应取完整 HMAC 输出最左侧的 $t$ bit \[5\]\[15\]。协议必须固定 $t$、编码方式、每个密钥允许的失败验证次数和密钥生命周期；若只验证 $t$ bit 标签，在线伪造概率还会受到攻击尝试次数与限流策略影响。没有明确协议依据时，优先保留完整 256 bit 标签。

## 11. 工程场景与选型边界

### 11.1 场景矩阵

| 场景 | 裸 SHA-256 是否足够 | 正确边界 |
| --- | --- | --- |
| 检测偶发传输损坏 | 通常可以 | 摘要需通过可信渠道获得；非对抗场景也可选普通校验和 |
| 软件包或镜像下载校验 | 取决于摘要来源 | 若文件和摘要来自同一可篡改渠道，攻击者可同时替换二者；应使用签名、透明日志或可信元数据 |
| 内容寻址、缓存键、去重 | 可以作为组件 | 必须固定字节序列化，考虑截断碰撞、算法标识和碰撞后的二次校验 |
| 数字签名 | 只能作为协议步骤 | 使用标准签名方案，绑定算法标识、对象类型、编码和上下文；不要自行设计“先哈希再加密” |
| 消息认证 | 不可以 | 使用 HMAC-SHA-256、KMAC、AEAD 或协议指定的认证构造 |
| 口令存储 | 不可以 | 使用 Argon2id、scrypt、bcrypt 或经审查的 PBKDF2 配置，配合唯一盐值和成本参数 \[7\]\[9\] |
| 密钥派生 | 不应直接使用裸哈希 | 使用 HKDF、PBKDF2 或协议规定的 KDF，并满足其输入密钥材料假设 |
| 加密 | 不可以 | 使用 AEAD 等标准加密方案；哈希摘要不能隐藏消息 |

### 11.2 字节级规范化

跨系统摘要不一致通常不是 SHA-256 本身出错，而是输入字节不同。协议必须明确：

- 文本编码，例如 UTF-8；
- Unicode 是否规范化，以及采用 NFC、NFD 等哪种形式；
- 换行是 LF 还是 CRLF；
- JSON 对象的字段顺序、数字格式、空白和转义规则；
- 文件是否包含 BOM；
- 二进制整数的宽度、符号和端序；
- 是否对压缩包、解压内容或规范化对象求哈希；
- 域分离前缀、版本号和对象类型是否进入哈希输入。

若业务实际上要对“抽象对象”求哈希，应先定义唯一的规范序列化；直接对各语言运行时的默认字符串或对象表示求哈希不可互操作。

### 11.3 域分离与算法敏捷性

同一哈希算法被多个协议目的复用时，可把固定、无歧义的上下文标签纳入输入：

$$
H(\text{domain-tag}\mathbin\Vert\text{encoded-message}).
$$

标签必须有规范的编码和边界，不能只依赖可能产生歧义的字符串拼接。更复杂的场景应采用已经提供域分离的标准构造。

持久化摘要时，不要只存 32 个匿名字节；应同时记录或由格式明确约束算法标识、版本、截断长度和编码。例如 `sha256:<64-hex>` 比一个没有上下文的十六进制串更利于迁移和审计。

### 11.4 流式处理、并行化与性能边界

流式调用 `update` 只改变数据送入实现的方式，不改变逻辑消息。只要字节顺序和内容相同，把文件按任意块大小依次输入，结果就与一次性哈希整个文件一致。

但标准 SHA-256 对单条消息具有链式依赖：

$$
H^{(i)}
=F\left(H^{(i-1)},M^{(i)}\right).
$$

第 $i$ 个分组需要前一分组的状态 $H^{(i-1)}$，因此不能把一个文件的各分块独立计算 `SHA256(chunk_i)`，再拼接或再次哈希这些分块摘要，并声称结果仍是该文件的标准 SHA-256。那会形成另一个树形或组合构造，其安全定义、编码和根摘要都必须由协议单独规定。

可利用的并行方式与实现级性能优化主要包括：

- 同时哈希多个相互独立的消息；
- 由成熟实现使用 CPU SHA 扩展、SIMD、指令级流水线或专用硬件；
- 使用协议明确规定的树哈希或并行哈希构造，而不是私自改变 SHA-256；
- 在不改变摘要语义的前提下优化 I/O，例如合理缓冲或内存映射。

吞吐量提升比例与 CPU、编译器、消息长度、内存层次和库实现高度相关。未经同平台基准测试，不应把某个实现的百分比或 GB/s 数值写成 SHA-256 算法本身的固定性能。

## 12. 与 SHA-512/256、SHA3-256 的区别

三者都输出 256 bit，但不是可互换算法：

| 算法 | 标准 | 基本构造与参数 | 经典通用碰撞强度 | 经典长度扩展 |
| --- | --- | --- | ---: | --- |
| SHA-256 | FIPS 180-4 | 512 bit 分组、32 bit 字、64 轮、SHA-2 迭代结构 | 128 bit | 存在 |
| SHA-512/256 | FIPS 180-4 | 1024 bit 分组、64 bit 字、80 轮、专用初始值后截断 | 128 bit | 不直接适用：输出隐藏了一半链式状态 |
| SHA3-256 | FIPS 202 | Keccak 海绵构造；Keccak-f[1600] 采用 24 轮，rate 为 1088 bit、capacity 为 512 bit | 128 bit | 不具有 SHA-256 式的经典长度扩展接口 |

SHA-512/256 不是“把普通 SHA-512 的结果随意截取 256 bit”：标准为它定义了不同的初始值。由于摘要没有暴露完整的 512 bit 链式状态，SHA-256 那种从公开摘要直接继续压缩的经典长度扩展步骤不能照搬；这仍不意味着可以据此自制 MAC。SHA3-256 也不是 SHA-256 的新编码，而是完全不同的构造 \[1\]\[10\]。

选型应优先服从协议互操作、平台支持、硬件特性、合规要求和既有数据格式。NIST 当前政策允许 SHA-2 与固定长度 SHA-3 算法用于安全哈希应用，并明确没有仅因 SHA-3 发布而迁移所有 SHA-2 应用的必要 \[13\]。

## 13. 常见实现错误与评审清单

### 13.1 算法实现错误

1. **把 byte 长度写入末尾字段。** 标准字段是原始消息的 bit 长度，即 `len(message) * 8`。
2. **在填充后才保存长度。** 长度字段必须记录原消息长度；`abc` 写入的是 24，不是 512。
3. **填充边界少一个分组。** 重点测试 55、56、63、64 byte。
4. **使用本机端序。** 消息字、长度字段和输出状态字均按大端序。
5. **忘记模 $2^{32}$。** Python 等任意精度整数实现必须显式掩码。
6. **错误处理按位取反。** Python 的 `~x` 需限制到 32 bit。
7. **混淆 $\Sigma$ 与 $\sigma$。** 旋转距离不同，小写函数还包含逻辑右移。
8. **消息调度下标错误。** 正确依赖是 $t-2,t-7,t-15,t-16$。
9. **顺序覆盖工作变量。** 每轮状态必须从旧值同步更新。
10. **漏掉每个分组后的前馈。** 多分组消息会立即暴露此错误。
11. **十六进制输出丢失前导零。** 每个状态字固定序列化为 4 byte。
12. **只验证 `abc`。** 单个短向量无法覆盖跨分组和填充边界。

### 13.2 应用设计错误

1. 把 `hexdigest()` 的 64 个字符误当作 512 bit 摘要；
2. 使用系统默认文本编码或不稳定对象序列化；
3. 用 `SHA256(secret || message)` 自制 MAC；
4. 用裸 SHA-256 存储口令；
5. 把从不可信渠道下载的摘要当作真实性证明；
6. 截断摘要却仍按完整 256 bit 评估强度；
7. 忽略算法标识、版本和域分离；
8. 只比较摘要，不在高风险去重场景核对长度、元数据或原始内容；
9. 使用普通字符串比较验证认证标签；
10. 自行维护密码学实现，而平台标准库已经满足需求。

### 13.3 评审清单

- [ ] 输入被定义为确定的字节串，而不是含糊的“文本”或“对象”。
- [ ] 明确使用完整 SHA-256 还是截断结果，并记录有效 bit 数。
- [ ] 完整性、真实性、口令存储、密钥派生等安全目标没有混用。
- [ ] 认证场景使用标准 HMAC、签名或 AEAD 构造。
- [ ] 大文件使用流式 API，不把整个文件读入内存。
- [ ] 摘要或标签来自可信渠道，并采用适合场景的比较方式。
- [ ] 实现通过空串、`abc`、56 byte 边界和多分组向量。
- [ ] 持久化格式包含算法标识和版本迁移策略。
- [ ] 合规场景使用经批准的实现与相应验证流程，而不是仅运行几个示例向量。

## 14. 结论

SHA-256 的规范核心可以概括为：

$$
\boxed{
\text{填充与分组}
\rightarrow
\text{64 字消息调度}
\rightarrow
\text{64 轮压缩}
\rightarrow
\text{逐分组前馈}
\rightarrow
\text{256 bit 摘要}
}.
$$

实现正确性依赖精确遵守 bit 长度、大端序、32 bit 模加法、Sigma 函数、同步状态更新和分组前馈。应用安全性则依赖更高一层的威胁模型：SHA-256 可提供内容指纹和密码学哈希能力，但不能独立提供来源认证、机密性或抗口令猜测能力。

工程上应优先使用成熟标准库，以标准测试向量验证互操作；需要认证时使用 HMAC-SHA-256 或协议指定构造，需要存储口令时使用专用口令哈希/KDF。只有把“算法本身的性质”和“协议如何使用它”分开，才能正确理解 SHA-256 的安全边界。
