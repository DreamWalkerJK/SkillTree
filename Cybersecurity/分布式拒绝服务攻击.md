# 分布式拒绝服务攻击（DDoS）：原理、检测、缓解与应急响应

> 本文从可用性工程和网络安全运营的角度，讨论分布式拒绝服务攻击（Distributed Denial of Service，DDoS）的威胁模型、资源耗尽机制、检测方法、分层防护和应急响应。示例只用于防御性监测与应用限流，不生成攻击流量；压力测试须在书面授权、隔离环境和明确的停止条件下进行。

## 1. 概念、范围与威胁模型

### 1.1 DoS 与 DDoS

拒绝服务（Denial of Service，DoS）攻击的目标是破坏服务的可用性，使合法用户无法建立连接、完成请求或获得及时响应。攻击源可以是单台主机，也可以是被控制的多个节点。DDoS 的“分布式”是指攻击流量由多个网络位置共同产生，或资源消耗请求由多个位置共同发起；这些来源可能是被恶意软件控制的终端、云主机、代理节点，也可能是被滥用的第三方服务（反射/放大）。

RFC 4732 将拒绝服务视为一种可用性攻击，而不是某一种固定的报文格式。攻击者只要能让链路、转发设备、连接状态、计算资源或业务依赖达到不可接受的负载，就可能造成拒绝服务。因此，“流量是否很大”不是判定 DDoS 的充分条件：一次低带宽但极其昂贵的业务请求，也可能耗尽应用线程池或数据库连接池。

需要区分以下几类现象：

| 术语 | 核心特征 | 与 DDoS 的关系 |
| --- | --- | --- |
| DoS | 以服务可用性损失为目标的广义攻击类别 | 上位概念 |
| DDoS | 多个来源协同制造资源耗尽或服务降级 | DoS 的分布式子类，本文重点 |
| 反射/放大 | 借助第三方服务响应，把流量导向受害者 | 常见于 DDoS，也可用于非分布式 DoS |
| 业务突发（flash crowd） | 大量真实用户同时访问，通常有明确业务原因 | 可能与 DDoS 高度相似；不能仅凭流量或意图判定 |
| 算法复杂度攻击 | 利用输入触发服务端算法的最坏复杂度 | 可作为应用层 DoS；哈希洪水攻击属于此类 |
| 资源误配置 | 配额、重试、日志或自动扩容策略失控 | 不一定是攻击，但会放大攻击影响 |

DDoS 主要影响可用性，并不自动意味着数据已经泄露或被篡改。事件响应时仍应分别检查机密性和完整性，避免把“服务不可用”与“数据安全事件”混为一谈。

业务突发与 DDoS 在统计特征上可能高度重叠。RFC 4732 指出，足够隐蔽的拒绝服务流量原则上无法只靠流量外观与正常突发区分；判断应结合变更记录、身份与业务成功率、请求成本以及多个观测点的证据。

### 1.2 受保护的资源

一次攻击可能跨越多个层次。分析时应把保护对象从“服务器”细化为可度量的资源：

| 资源 | 常用指标 | 典型耗尽方式 |
| --- | --- | --- |
| 接入链路 | bit/s、接口利用率、丢包率 | 大流量洪泛、反射放大 |
| 转发与内核 | packet/s、每秒新流数、软中断、CPU | 小包洪泛、协议异常 |
| 状态表 | conntrack 条目、SYN backlog、并发连接数 | SYN 洪泛、长连接耗尽 |
| 加密与协议处理 | TLS 握手率、CPU 时间、握手失败率 | TLS 握手耗尽、协议状态机滥用 |
| Web/API 层 | 请求率（RPS）、并发请求、响应延迟、5xx | HTTP 洪泛、慢请求、缓存穿透 |
| 下游依赖 | 数据库连接、队列长度、外部 API 配额 | 昂贵查询、重试风暴、级联故障 |
| 控制平面 | DNS 查询、路由变更、管理接口负载 | 控制平面被挤占、应急操作失效 |

资产清单应记录每项资源的容量、依赖关系、观测位置和降级策略。只监控主机 CPU，往往无法解释为什么用户已经超时。

## 2. 资源耗尽模型

### 2.1 排队关系

设某资源的到达率为 $\lambda$，该资源在服务等级目标（Service Level Objective，SLO）下的可持续服务率为 $\mu$。队列长度可以用下式作近似：

$$
Q_{t+\Delta t}=\max\left(0,\;Q_t+(\lambda-\mu)\Delta t\right)
$$

其中 $Q_t$ 是时刻 $t$ 的队列长度，$\Delta t$ 是观察间隔。该近似忽略了服务率随负载变化、丢弃和重试等细节，用于说明资源压力的变化趋势。

当利用率 $\rho=\lambda/\mu$ 接近 1 时，延迟会对微小的流量变化非常敏感；当 $\rho>1$ 时，系统积压会持续增加，有限队列随后触及上限，表现为丢包、超时、拒绝或级联故障。这里的工作单位不一定是 HTTP 请求，也可以是报文率、握手率、并发连接数或数据库查询率。

在稳定的排队系统中，还可以用 Little 定律估算并发量：

$$
L=\lambda W
$$

其中 $L$ 是系统中的平均并发工作数，$W$ 是平均停留时间。攻击者不必把 $\lambda$ 提高到极大；只要让单个请求的处理时间 $W$ 显著增加，就能在有限的请求率下把并发量推到上限。这正是慢请求、昂贵查询和握手型攻击的共同特点。

不同资源的计量单位不同，不能直接把 bit/s、packet/s、连接数和 CPU 值取最小值。对资源 $i$ 定义归一化利用率：

$$
\rho_i(t)=\frac{\operatorname{load}_i(t)}
{\operatorname{capacity}_i}
$$

其中 $i$ 表示链路、转发、状态、CPU 或下游依赖等资源。同一时刻的最大资源压力可写为 $\rho_{\max}=\max_i\rho_i$，对应的主要瓶颈为 $i^*=\arg\max_i\rho_i$；当 $\rho_{\max}$ 接近 1 时，说明余量已经很小，超过 1 则表示至少有一项资源超出 SLO 要求下的可持续容量。在统一的业务工作量定义和固定拓扑下，可以用瓶颈资源对应的容量估计有效容量；简单取多个容量值的最小值，只有在各项已经换算到同一单位时才成立。

因此，增加应用实例数并不能解决已经在上游链路或负载均衡器处发生的饱和；同样，购买更大的带宽也不能替代对数据库和线程池的保护。

### 2.2 反射与放大

在反射攻击中，攻击者伪造源地址，把请求发送给会向受害者回复的第三方服务。UDP 本身不提供类似 TCP 三次握手的端点可达性验证，因此更容易被伪造源地址的报文滥用；这并不等于 TCP 对源地址提供了密码学认证，具体应用仍可能实现自己的请求校验。若按同一统计口径，受害者收到的响应字节数为 $R$，攻击者实际发出的请求字节数为 $S$，可以定义观测到的放大因子：

$$
A=\frac{R}{S}
$$

A 不是协议的固定属性，会随请求内容、服务实现、缓存状态和过滤策略变化。防御重点包括：

- 网络运营商和组织应在网络边缘对来自客户或租户接口的出站流量实施源地址过滤或验证，落实 BCP 38（RFC 2827）和 RFC 3704，减少源地址伪造；
- 关闭不必要的公网 UDP 服务，限制递归 DNS（RFC 5358）、管理接口和诊断协议的访问范围；
- 在上游网络或清洗服务按目的地址、协议、端口和包速率进行过滤；
- 不把“某个协议的典型放大倍数”当作容量规划依据，实际容量应以监测数据和供应商保证为准。

反射流量中的源地址可能是伪造的，IP 地理位置、ASN 或单个地址不能直接用来认定攻击主体，也不应据此采取报复性措施。

## 3. 攻击类型与作用机制

下列分类按照被消耗的资源组织，便于将观测到的症状映射到相应的控制措施。真实事件经常是多种类型叠加，并在防护生效后切换到另一层。

CISA、FBI 与 MS-ISAC 在 2024 年联合发布的指南也采用体积型、协议型和应用层三类划分，并强调多向量攻击需要组合处置。

### 3.1 体积型攻击（Volumetric）

体积型攻击主要消耗接入链路容量或网络设备的转发能力，指标通常以 bit/s 或 packet/s 衡量。

- **UDP/ICMP/GRE 等洪泛**：大量报文直接消耗链路、路由器队列和主机软中断。小包攻击往往以较低的 bit/s 造成较高的 packet/s 压力。
- **反射/放大洪泛**：借助 DNS、NTP、SSDP、CLDAP、Memcached 等暴露在公网且配置不当、可通过 UDP 提供服务的实例转发响应。列举协议并不意味着这些协议本身必然不安全，风险取决于部署是否限制请求来源、关闭公开递归并隔离管理面。
- **多协议混合**：同时改变协议、端口和包长，试图规避固定 ACL。此时应优先交由上游清洗服务处理，并以流量基线和受保护资源为依据合并过滤条件。

体积型攻击一旦填满受害者与上游之间的链路，应用层 WAF、主机防火墙和本地限流即便能够看到报文，也无法在已饱和的链路上恢复可用性；流量必须在链路饱和之前由运营商的上游 DDoS 清洗服务、云清洗平台或 Anycast/CDN 节点处理。

### 3.2 协议与状态耗尽

协议型攻击不一定产生极高带宽，但会耗尽连接状态、协议解析或内核资源。

- **TCP SYN 洪泛**：大量 SYN 使服务端在收到最终 ACK 前保留半连接状态，可能耗尽 SYN backlog 或中间设备的连接跟踪表。SYN cookies、合理的 backlog、上游 SYN proxy 和连接速率限制是常见缓解手段。SYN cookies 的具体副作用取决于操作系统实现，启用后应验证 TCP 选项和高延迟链路上的表现。
- **ACK/RST 与连接跟踪耗尽**：伪造或异常的后续报文会增加防火墙、NAT 和 conntrack 的处理成本。分布式环境中的非对称路由还可能使状态设备无法正确匹配连接。
- **分片和异常报文**：大量分片、重叠分片或畸形头部可能消耗重组缓存和解析 CPU。应在网络入口设备规范化或丢弃不符合策略的报文，并确认 IPv4 与 IPv6 的处理策略一致。
- **TLS/QUIC 握手耗尽**：握手阶段的非对称加密和证书处理成本高于保持一个已建立连接。可在边缘终止 TLS、启用会话恢复、限制每源和全局握手速率，并对 QUIC/HTTP/3 的 UDP 入口设置独立配额。
- **协议状态机滥用**：HTTP/2 的快速重置（Rapid Reset，CVE-2023-44487）通过快速创建并取消大量 HTTP/2 流（RST_STREAM）形成请求序列，说明协议层面看似合规的流操作组合也可能触发高成本状态转换。应及时应用厂商补丁、限制并发流和重置速率，并关注组件公告。

### 3.3 应用层攻击

应用层攻击直接消耗 Web 服务器、业务代码或下游依赖的处理能力，常见指标是请求率（RPS）、并发请求、响应延迟和错误率。

- **HTTP 请求洪泛**：请求看似合法，却集中访问未缓存或计算昂贵的路径，例如复杂搜索、报表和文件转换。单纯按 IP 限流在代理池或大规模 NAT 场景下通常不足。
- **缓存穿透与缓存旁路**：不断改变查询参数、请求头或不可缓存方法，使每次请求都到达源站。应设计明确的缓存键、参数规范化和未命中预算。
- **慢请求（Low-and-slow）**：故意以极低速率发送请求头或请求体，长期占用连接、缓冲区、文件描述符以及可能的线程或协程资源。应设置请求头/体读取超时、最小接收速率、并发连接上限和隔离的工作池。
- **长连接和升级协议**：WebSocket、长轮询和 HTTP/2 多路复用会改变“一个连接对应一个请求”的假设，需要同时限制连接数、流数、消息大小和空闲时间。
- **重试风暴**：客户端、网关和服务之间没有退避或预算时，攻击流量会被重试机制放大。应使用指数退避、抖动、全链路重试预算和熔断。
- **算法复杂度攻击**：可控输入触发哈希表、正则表达式或解析器的最坏复杂度。参见[哈希洪水攻击](./哈希洪水攻击.md)，并把输入约束放在解析和分配之前。

应用层防护应按处理成本从低到高执行检查：先核验连接和请求预算、身份与租户配额、缓存规则和格式约束，再访问数据库或外部服务。

### 3.4 多向量攻击与跨层迁移

攻击者可能同时消耗带宽、连接状态和应用 CPU，或在一种缓解措施生效后切换到另一种向量。防护系统应协调部署流量清洗、边缘限流、应用降级和下游隔离，而不是只配置一条 WAF 规则。

## 4. 从准备到恢复：攻击生命周期

一次事件通常包含以下阶段，阶段之间可能反复切换：

1. **准备与探测**：寻找暴露的服务、可缓存路径、认证入口和容量阈值。
2. **启动与爬升**：流量从低到高，观察超时、限流和错误响应。
3. **持续与变形**：改变来源、协议、请求特征或时间分布，规避固定规则。
4. **缓解与迁移**：防护方启用清洗、限速、缓存或黑洞后，攻击者可能转向另一层。
5. **退出与复盘**：流量下降并不代表根因消失，需要确认临时策略、配置和依赖恢复正常。

准备阶段应建立“正常行为”的基线。没有基线时，事件中很难区分攻击、营销活动、版本发布和依赖故障。

## 5. 检测与诊断

### 5.1 观测分层

建议采集指标时至少覆盖网络入口、网关、应用、主机和下游依赖，并同步记录业务影响；时间戳统一采用 UTC，或在记录中明确注明时区。

| 观测位置 | 指标示例 | 诊断问题 |
| --- | --- | --- |
| 网络入口/清洗服务 | bit/s、packet/s、协议分布、目的端口、丢包、NetFlow/IPFIX | 链路或转发面是否先饱和 |
| 负载均衡 | 新建连接率、SYN/ACK 比、活动连接、后端健康率 | 状态表或后端连接是否耗尽 |
| API/WAF | RPS、状态码、p95/p99、缓存命中率、规则命中 | 请求是否集中到昂贵路径 |
| 主机运行时 | CPU/软中断、内存、GC、线程池、文件描述符 | 哪一种本地资源达到上限 |
| 下游依赖层 | DB 连接/锁等待、队列长度、外部 API 配额 | 是否出现级联故障或重试放大 |
| 业务 | 登录成功率、订单转化、租户维度错误率 | 合法用户的实际影响范围 |

单一指标不能证明 DDoS。例如，CPU 升高可能来自发布后的死循环，RPS 升高可能是营销活动。判定应尽可能关联“流量异常”“资源饱和”和“合法用户受影响”等多类证据，但不应把所有维度同时异常作为必要条件，并对照最近的发布、DNS、证书和配置变更。

### 5.2 基线与异常分数

可以用滑动窗口、按星期和时段分组的历史样本建立基线。对于含有尖峰的指标，中位数和中位绝对偏差（MAD）比平均值和标准差更稳健：

$$
\mathrm{MAD}=\operatorname{median}(|x_i-\operatorname{median}(x)|)
$$

$$
z_{\mathrm{robust}}=\frac{x-\operatorname{median}(x)}
{\mathrm{MAD}/0.6745}
$$

式中的 0.6745 是标准正态分布下用于将 MAD 换算为尺度估计的常数。MAD 为零时应设置最小尺度，不能直接除零。阈值没有通用标准值；页面告警、值班通知和自动封禁应分别校准，并加入发布日历、节假日和业务活动等上下文。

下面的 Python 示例只处理已经采集的指标，不主动向外部目标发送网络流量。它要求至少两个相互补充的指标同时异常，以降低把正常业务突发误判为攻击的概率；代码并不假设这些指标在统计上相互独立。
示例使用 Python 3.9 及以上版本的类型注解。

~~~python
from collections.abc import Iterable, Mapping
from statistics import median


def robust_z_score(value: float, history: Iterable[float]) -> float:
    samples = [float(item) for item in history]
    if len(samples) < 5:
        raise ValueError("baseline needs at least five samples")

    center = median(samples)
    mad = median(abs(item - center) for item in samples)

    # MAD=0 常见于低波动指标；设置最小尺度避免除零。
    scale = mad / 0.67448975 if mad > 0 else max(abs(center) * 0.1, 1.0)
    return (float(value) - center) / scale


def detect_overload(
    current: Mapping[str, float],
    baseline: Mapping[str, Iterable[float]],
    score_threshold: float = 6.0,
) -> tuple[bool, dict[str, float]]:
    scores = {
        name: robust_z_score(current[name], values)
        for name, values in baseline.items()
        if name in current
    }
    abnormal = {name: score for name, score in scores.items()
                if score >= score_threshold}

    # 这里只产生告警信号；封禁和路由变更必须经过策略引擎与人工审批。
    return len(abnormal) >= 2, abnormal


if __name__ == "__main__":
    current = {"rps": 4200, "p95_ms": 1800, "error_rate": 0.21}
    baseline = {
        "rps": [280, 310, 295, 340, 305, 325, 300],
        "p95_ms": [180, 210, 190, 205, 200, 195, 215],
        "error_rate": [0.01, 0.012, 0.009, 0.011, 0.013, 0.01, 0.012],
    }
    page, signals = detect_overload(current, baseline)
    print({"page": page, "signals": signals})
~~~

这里的“双指标”是示例告警策略，不是判定 DDoS 的普遍门槛；对于只影响单一资源的攻击，仍应结合该资源的遥测和业务影响单独分析。

生产实现还应考虑指标方向（例如丢包率升高而缓存命中率下降）、每租户基线、缺失数据、采样偏差和告警抑制。异常分数只能辅助判断，不能直接作为自动封禁的唯一依据。

### 5.3 诊断顺序

收到告警后可按以下顺序缩小范围：

1. **确认影响面**：比较边缘、源站、各区域和各租户的成功率，确认是全局不可用还是单一入口异常。
2. **排除变更因素**：检查最近的发布、DNS/证书、路由、WAF 和容量配置变更。
3. **定位瓶颈层**：先看链路和 packet/s，再看连接状态、TLS/HTTP 指标，最后检查应用和数据库。
4. **识别流量特征**：协议、目的端口、请求路径、认证状态、User-Agent、ASN（自治系统号）和地域只能作为组合证据的一部分，不能单独作为封禁依据。
5. **验证合法业务**：抽样检查已登录用户、关键交易和健康检查，避免把业务高峰当成攻击。
6. **记录证据**：保存带时区的流量摘要、日志查询、配置变更、供应商工单和每次缓解动作的时间线。

## 6. 分层防护架构

### 6.1 参考路径

常见的防护链路如下，实际部署可以合并或省略某些组件：

~~~text
解析控制平面：
客户端 ── DNS 查询 ──> 权威 DNS
客户端 <── 返回 Anycast/CDN 地址 ── 权威 DNS

业务数据平面：客户端 ──> Anycast/CDN/上游 DDoS 清洗服务
                           │
                           ▼
                    L4 负载均衡
                           │
                           ▼
                 WAF / API 网关 / 限流
                           │
                           ▼
              源站屏蔽层（Origin Shield）/ 私有网络
                           │
                           ▼
       应用服务 ── 缓存 ── 异步队列 ── 数据库与外部依赖
~~~

权威 DNS 只负责名称解析，不承载 HTTP/UDP 业务转发；DNS 查询服务本身也需要独立的冗余、监控和防护。

源站地址应尽量不直接暴露，管理平面与业务数据平面分离，健康检查走独立的低成本路径。

Anycast、CDN 和清洗服务只能把处理位置前移，不能替代源站的配额、超时和下游依赖隔离。清洗或 CDN 只保护已经接入其网络、且在其识别范围内的流量；旁路域名和直接访问源站 IP 不会自动获得同等保护。

### 6.2 组织和网络层

- **源地址验证**：在网络边缘对来自租户或客户侧的出站流量实施源地址过滤、单播反向路径转发（uRPF）或等效机制，按 RFC 2827、RFC 3704 的原则减少伪造源地址。严格（strict）uRPF 要求反向最佳路径匹配入接口，适合路由对称的网络。存在非对称路由时，应评估 loose（只要求存在可达路由）或 feasible-path 模式，避免把合法返回流量误丢弃。
- **路由安全**：NIST SP 800-189 将源地址验证、资源公钥基础设施（RPKI）、路由异常和跨域流量交换放在同一风险模型中。涉及 BGP 的改动应由网络团队和上游运营商共同评审。
- **上游清洗服务**：与运营商或云服务商约定启用条件、路由切换方式、可接受的误拦截率、数据保留和费用模型。清洗服务应在链路饱和前接管流量。
- **FlowSpec/RTBH**：BGP FlowSpec（RFC 8955）可在上游按流特征下发过滤；远程触发黑洞（RTBH，RFC 5635；RFC 7999 定义了用于此目的的 BLACKHOLE BGP 社区）能快速保护网络，但通常会同时丢弃合法流量，只适合作为明确授权的最后手段。应先确认供应商支持，再完成路由权限校验和误配置检查，并保留观察窗口与回滚路径。
- **状态与速率保护**：为新连接、TLS 握手、UDP 会话和分片重组设置独立预算；限制队列长度，避免“排队等待”把内存耗尽。
- **管理平面隔离**：将 DNS、路由、监控和应急入口放在与业务流量不同的管理网络或带外通道，参照 RFC 6192 保护路由器和网络控制平面，确保攻击期间仍能操作。

### 6.3 应用层与下游依赖

- 对请求体大小、参数数量、嵌套深度、上传速率和读取超时设定上限，并在解析前拒绝超限输入。
- OWASP API Security Top 10（2023）的 API4“Unrestricted Resource Consumption”将批量操作、资源配额、执行超时和云成本列为同一类风险；API 设计时应把这些限制写入接口契约，而不只依赖网关临时配置。
- 使用令牌桶、漏桶或固定窗口限制请求率；同时设置并发上限和队列上限。队列满时快速返回 429/503，避免无限等待；429 适合表示请求级限流，503 可表示暂时无可用服务，两者都不能替代网络层清洗。
- 限流键应按风险选择：认证用户、租户、API 密钥、源地址和全局预算可以组合使用。经过反向代理时，只信任明确配置的代理网段，不要直接相信任意客户端提交的 X-Forwarded-For。
- 通过缓存、请求合并、幂等键和异步队列降低重复计算；把报表、搜索、文件转换等昂贵操作放到隔离的资源池。
- 为数据库和外部 API 设置连接池、查询超时、并发配额和重试预算。限流只保护 Web 层而不保护下游，仍可能发生级联故障。
- 对关键功能设计降级：只读模式、静态响应、将非关键任务异步处理或推迟执行、关闭高成本筛选项。降级开关应可审计、可回滚并有过期时间。
- WAF 规则应基于行为和业务上下文逐步收紧。挑战页面可能影响无头客户端、无障碍用户和 API 调用，不能作为唯一方案。CAPTCHA 或计算谜题主要用于抑制功能滥用，无法替代对链路洪泛和协议状态耗尽的上游防护。

令牌桶把短时突发和长期平均速率分开控制：桶容量决定允许的瞬时突发，补充速率决定长期预算。生产系统还要为每个接口设置不同的成本权重，避免把“一个请求”误当成相同的资源消耗。

### 6.4 控制措施的适用范围与局限

| 控制 | 擅长处理 | 不能单独解决的问题 | 主要副作用 |
| --- | --- | --- | --- |
| 上游清洗服务/Anycast | 大带宽、分布式网络洪泛 | 源站昂贵查询、错误重试 | 成本、额外延迟、供应商依赖 |
| CDN 缓存 | 可缓存的 GET/静态资源 | 不可缓存的 POST、源站逻辑缺陷 | 缓存一致性与隐私配置复杂 |
| WAF | HTTP 特征和业务规则 | 已填满的接入链路、未知协议状态耗尽 | 误报、规则计算开销 |
| 应用限流 | 用户/租户/接口级突发 | 上游链路已饱和、伪造源地址 | 合法大客户被误限 |
| 自动扩容 | 可预测的合法业务增长 | 带宽、状态表和数据库瓶颈 | 成本放大、依赖级联 |
| SYN cookies | 半连接状态耗尽 | UDP/HTTP 洪泛和链路饱和 | 具体 TCP 选项行为需验证 |
| RTBH 黑洞 | 快速保护上游网络 | 保留该地址的业务可用性 | 合法流量一并丢弃 |

### 6.5 ASP.NET Core 应用限流示例

ASP.NET Core 在 .NET 7 及更高版本提供 Rate Limiting Middleware。下面的示例为每个认证用户或源地址分配令牌桶，并将队列设置为零，使过载请求立即失败。60 次/分钟只是演示值，生产参数应由接口成本、SLO 和租户合同共同决定。
示例假设认证中间件已经正确配置；未认证请求按源地址维度限流。
本例 TokenLimit 和 TokensPerPeriod 均为 60，表示每个分区最多积累 60 个令牌，长期平均补充速率约为每秒 1 个请求。

~~~csharp
using System.Threading.RateLimiting;
using System.Threading.Tasks;
using Microsoft.AspNetCore.RateLimiting;

var builder = WebApplication.CreateBuilder(args);

builder.Services.AddRateLimiter(options =>
{
    options.RejectionStatusCode = StatusCodes.Status429TooManyRequests;
    options.OnRejected = (context, _) =>
    {
        context.HttpContext.Response.Headers["Retry-After"] = "60";
        return ValueTask.CompletedTask;
    };

    options.AddPolicy("api", httpContext =>
    {
        var subject = httpContext.User.FindFirst("sub")?.Value
                      ?? httpContext.User.Identity?.Name;
        var key = !string.IsNullOrWhiteSpace(subject)
            ? "user:" + subject
            : "ip:" + (httpContext.Connection.RemoteIpAddress?.ToString() ?? "unknown");

        return RateLimitPartition.GetTokenBucketLimiter(
            partitionKey: key,
            factory: _ => new TokenBucketRateLimiterOptions
            {
                TokenLimit = 60,
                TokensPerPeriod = 60,
                ReplenishmentPeriod = TimeSpan.FromMinutes(1),
                QueueProcessingOrder = QueueProcessingOrder.OldestFirst,
                QueueLimit = 0,
                AutoReplenishment = true
            });
    });
});

var app = builder.Build();

// 如果应用位于反向代理后，应先配置 KnownProxies/KnownNetworks，
// 再调用 app.UseForwardedHeaders()。
app.UseRouting();
// 如果启用了认证，应在此处先调用 UseAuthentication()，再执行限流。
// app.UseAuthentication();
app.UseRateLimiter();

app.MapPost("/api/orders", () => Results.Accepted())
   .RequireRateLimiting("api");

app.Run();
~~~

这段代码只在应用已经收到请求后生效，无法缓解接入链路或负载均衡器之前的体积型攻击。429 响应中的 Retry-After 可帮助客户端退避（参见 RFC 6585）；是否返回以及返回多久，应由 API 语义和客户端重试约定决定，本例的固定 60 秒仅用于演示。

部署在代理后时，必须使用 ASP.NET Core 的 Forwarded Headers Middleware，并显式配置可信代理/网络；否则按 IP 分区可能把所有用户错误地归到代理地址，或者被客户端伪造的转发头绕过。

示例使用进程内分区，多实例部署时每个实例各自计数，并不等于全局配额；大量轮换用户标识或地址还可能造成高基数分区和内存压力。

生产系统应叠加全局预算、并发限制、限制分区数量并淘汰闲置分区，或采用分布式限流，并为认证中间件、代理信任链和故障回退制定明确策略。

## 7. 应急响应运行手册

下面的流程可参照 NIST SP 800-61 Rev. 3 的准备、检测、响应、恢复和持续改进思路；DDoS 事件的具体角色、权限和时限仍需结合组织的值班制度与供应商 SLA 确定。

### 7.1 事件前准备

准备阶段要将临时处置落实为可审计、可回滚的配置变更：

- 为域名、IP、证书、端口、源站和关键依赖建立资产清单，标出业务优先级与最大可接受中断时间。
- 记录 ISP、云厂商、CDN/WAF、注册商和内部值班人员的 24×7 联系方式，提前确认升级路径和授权人。
- 为清洗、限流、降级、故障转移和 RTBH 准备经过评审的变更模板，定义启用条件、观察窗口和回滚动作。
- 建立链路、接口、连接、应用和业务指标的基线；日志中统一保留请求 ID、时间戳和代理链信息。
- 在不使用真实用户数据的前提下，定期做桌面推演和受控演练，验证告警、权限、供应商响应和恢复步骤。

### 7.2 事件中分阶段处置

下表中的时间窗是便于演练的示例，不是统一的行业标准；实际时限应按组织值班安排、供应商 SLA 和事件严重度调整。

| 阶段 | 关键动作 | 结束条件 |
| --- | --- | --- |
| 发现（0–5 分钟） | 确认告警来源与时间窗；比较边缘和源站；检查最近变更；建立事件编号 | 明确影响范围和疑似瓶颈 |
| 遏制（5–15 分钟） | 通知上游/清洗服务；启用已批准的边缘限速、缓存和降级；保护管理平面 | 合法用户成功率恢复并在观察窗口内保持稳定，核心资源不再持续增长 |
| 稳定（15–60 分钟） | 逐步收紧或放宽规则；按路径和租户评估误拦截；隔离数据库和外部依赖；持续取证 | 关键 SLO 在观察窗口内稳定 |
| 恢复 | 按变更记录回滚临时策略；验证 DNS、路由、缓存、队列和数据一致性 | 服务恢复正常且无残留过载 |
| 复盘 | 形成时间线、容量缺口、误报/漏报和供应商表现 | 明确改进项的负责人、完成期限和验证方式 |

不要在事件中进行反向攻击、扫描攻击源或发送报复性流量。此类行为可能违法，也会扩大影响面。若怀疑同时存在入侵或数据泄露，应按独立的安全事件流程保全证据并通知法务、隐私和监管联系人。

### 7.3 证据与沟通

证据应保留原始时间、时区和采样方法，至少包括：

- NetFlow/IPFIX/sFlow 摘要、接口计数器和清洗服务报告；
- 负载均衡、WAF、应用、数据库和系统日志，以及关键请求的脱敏样本；
- WAF/ACL/路由/扩容/降级等配置变更前后的版本和操作者；
- 供应商工单、电话沟通时间点、路由切换和恢复确认；
- 对导出的文件计算哈希并记录保存位置（可参阅 [SHA-256：标准流程、压缩函数、安全性质与工程实践](../Cryptography/SHA-256.md)），确保复盘时可以验证完整性。

对外沟通应只披露已确认的事实、影响范围、临时措施和下一次更新时间。不要公开可被再次利用的源站地址、内部拓扑或未验证的攻击归因。

## 8. 容量规划与安全测试

### 8.1 规划维度

容量评估应分别测量带宽、packet/s、新建连接率、并发连接、TLS 握手率、应用 RPS、下游查询率和日志吞吐。每项都应在目标 p95/p99 延迟和错误率下测量，而不是只看理论峰值。由于这些指标的单位不同，报告中应保留各自的容量和利用率。

在统一的业务工作量口径下，可以为每个入口定义：

- 正常峰值 $\lambda_{\mathrm{normal}}$；
- 在目标 SLO 下的可持续容量 $C_{\mathrm{effective}}$；
- 保护余量 $H=(C_{\mathrm{effective}}-\lambda_{\mathrm{normal}})/C_{\mathrm{effective}}$（带宽、packet/s、连接和下游查询应分别计算）；
- 触发清洗、降级和人工升级的阈值。

若 $H<0$，说明正常峰值已经超过该资源在目标 SLO 下的可持续容量，应先修复容量或负载模型，再讨论攻击余量。

余量不是越大越好：过高会造成不必要的资源成本，过低则无法吸收合法突发。阈值应结合业务季节性、供应商切换时间和恢复目标定期重估。

### 8.2 受控演练原则

在生产环境做任何流量演练前，应取得资产所有者、云厂商/运营商和相关业务方的书面批准。演练至少满足以下条件：

1. 使用隔离的测试域名、地址段和身份；禁止源地址伪造、第三方反射和向公共互联网扩散。
2. 预先定义速率、持续时间、停止条件、联系人和回滚步骤；把“合法用户成功率下降”设为明确的终止条件。
3. 先验证监控和告警，再逐步增加受控的合成请求；不要使用真实凭据或不可逆业务操作。
4. 演练期间监控网络入口、网关、应用、数据库、费用和供应商保护状态；结束后确认临时规则已经清理。
5. 输出可重复的报告：假设、拓扑、输入、观测、偏差、结论和后续改进。

这类演练的目的，是验证检测、沟通、切换和恢复能力，而不是追求某个最大流量指标或峰值规模。没有上游授权时，不应在公网进行高流量试验。

## 9. 常见误区

- **“带宽够大就不会被 DDoS。”** 小包、高连接率或昂贵请求可以先耗尽 packet/s、状态表或 CPU。
- **“自动扩容可以解决攻击。”** 扩容对上游链路和状态表无效，还可能把攻击成本转化为云账单和数据库级联压力。
- **“封禁几个 IP 就结束了。”** 分布式来源、NAT 和代理会让 IP 维度不稳定；应组合身份、租户、路径和全局预算。
- **“WAF 能拦截所有 DDoS。”** WAF 只能在请求到达它之后工作，无法替代上游清洗和网络容量。
- **“SYN cookies 开启后万事大吉。”** 它主要缓解半连接状态耗尽，不能处理 UDP、HTTP 或链路饱和。
- **“接入 CDN 后源站自然安全。”** 源站 DNS 记录、证书、错误页面和旁路域名可能暴露源站；已知源站 IP 的直接访问还可能绕过 CDN 或清洗层。
- **“看到 5xx 就认定是攻击。”** 发布缺陷、数据库故障和配置错误同样会造成 5xx；必须关联变更与流量证据。
- **“记录越多越好。”** 攻击期间同步写入大量详细日志会进一步耗尽磁盘、CPU 或日志管道，应采用采样、分级和限额。
- **“把所有 UDP 或所有海外地址都封掉。”** 这可能误伤 DNS、QUIC、VoIP 等 UDP 业务；粗粒度的地址封禁还可能影响 IPv6 控制报文（ICMPv6）和合法跨境业务。策略应按资产和业务需求细化。

## 10. 小结

DDoS 防护的核心，是为各层资源设置可测量的容量、限流规则和响应动作：

1. 用资产、容量和 SLO 识别最先耗尽的资源；
2. 在网络入口、协议、应用和依赖层采集可关联的信号；
3. 让流量在最靠近来源的位置被吸收、清洗或拒绝；
4. 在应用内为请求、并发、队列和下游调用设置明确上限；
5. 用可审计的运行手册完成升级、降级、恢复和复盘。

检测、架构和应急流程在同一事件时间轴上协同运行，DDoS 才会从不可预测的“网络灾难”变成可以度量和演练的可用性风险。
