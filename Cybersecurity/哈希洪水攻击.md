# 哈希洪水攻击（Hash-Flooding Attack）

## 原理

哈希洪水攻击（Hash-Flooding Attack）又称哈希冲突拒绝服务攻击（Hash DoS），是一种拒绝服务攻击（Denial of Service）。

其利用有些数据结构的“平均运行时间”和“最差运行时间”相差甚大的特点，利用算法上的漏洞，强行构造出一个最差情况，让服务器把全部资源都浪费在处理这个最差情况上。

更准确地说，哈希洪水攻击利用的是哈希表在平均时间复杂度和最坏时间复杂度之间的差异，属于算法复杂度攻击。哈希碰撞本身是正常现象；只有当外部输入可控，并且攻击者能够集中制造碰撞时，才会形成可利用的拒绝服务风险。

比如哈希表（Hash Table），假设想要连续插入 `n` 个元素到哈希表中：

- 如果这些元素的键（Key）极少发生碰撞，通常只需要 `O(n)` 的时间。
- 如果这些键频繁发生碰撞，出现相同的哈希值，最坏情况下可能需要 `O(n²)` 的时间。

哈希表在理想情况下，数据均匀分布，查询的平均时间复杂度为 `O(1)`。当发生哈希碰撞时，常见解决方案是使用链表将冲突元素串联在同一槽位。

利用哈希表在处理大量冲突时的性能退化，构造足够数量的、具有相同哈希值或被映射到同一槽位的字符串，这些数据被映射到同一个哈希槽位，哈希表退化成长链表。单个元素的查询和需要检查重复键的插入操作，时间复杂度会从 `O(1)` 恶化成 `O(n)`。接着将这些数据提交到后台服务器，使哈希表性能退化，就能用很低的成本将服务器瘫痪。

这里的 `O(n²)` 是连续处理 `n` 个碰撞键时可能出现的总时间复杂度。具体结果取决于哈希表的实现方式：例如，单纯在链表头部插入元素可以保持 `O(1)`，但查询、更新以及插入前的重复键检查仍可能需要遍历整条链表。

## 攻击实施条件

实施哈希洪水攻击需要满足两个前提：

- **哈希函数已知或可预测**：攻击者能够分析出目标系统的哈希函数或计算规律。
- **能够批量提交数据**：攻击者可以通过 HTTP 请求参数、表单提交等途径，向服务器批量发送大量构造数据。

如果哈希表使用不可预测的随机种子，或者应用在数据进入哈希表之前已经限制了参数数量和请求大小，攻击者构造并提交大量定向碰撞数据的难度就会明显增加。

## 防御

### 带随机种子的哈希函数（SipHash）

**适用场景：** 所有哈希表操作

为了降低针对性碰撞攻击的可行性，如果找到更优秀的哈希算法，让那些元素的键的哈希值完全不发生碰撞，是不是就能解决问题？

答案是不行。在均匀随机模型下，哈希碰撞的概率主要取决于两个因素：

- 取值空间的大小（即哈希值的长度）。
- 整个生命周期中，哈希值的计算次数。

这个问题与数学上的[生日悖论](../Mathematics/生日悖论.md)一致。假如取值空间为 365，那么计算 23 次，产生哈希碰撞的概率就已经超过 50%；计算 60 次，产生哈希碰撞的概率就已经超过 99%。也就是说，两个不同字符串经过哈希算法计算后，存在一定概率得到相同的哈希值，并且随着计算次数增加，发生至少一次碰撞的概率也会增大。

这是种反直觉的现象。若只考虑组中的某个人，组中其他人的生日与该人的生日相同的概率很小；然而，生日悖论考虑的是组内任意两个人生日相同的概率。

需要区分哈希码的取值空间和哈希表的槽位空间。完整哈希码可能有 32 位或 64 位，但最终仍要映射到数量有限的槽位中。因此，不同哈希码也可能落入同一个槽位。哈希洪水攻击只要求大量键集中到同一个槽位或冲突簇，并不一定要求它们的完整哈希码完全相同。

如果攻击者掌握哈希算法、随机种子和槽位映射规则，就可能通过离线搜索或利用算法特征构造大量碰撞键；是否能够高效构造，还取决于具体算法和实现，不能简单认为掌握算法细节后就一定能算出碰撞键。

反过来，如果攻击者无法获知随机种子，就很难提前计算出针对当前进程或当前哈希表的碰撞键，但这并不意味着攻击完全不可能发生。大量随机输入仍会消耗解析、分配和哈希计算资源，因此随机化需要和请求规模限制配合使用。

比如在算法中加入一个其他人都不知道的秘密参数，在进程启动或创建哈希表时随机生成。这样即使是完全相同的内容，在秘密参数不同的情况下，也可能产生不同的哈希结果和槽位分布，使整个过程难以预测。这个秘密参数被称为哈希种子（Hash Seed）；使用秘密参数参与计算的哈希算法，也可以称为带密钥哈希算法（Keyed Hash Function）。

这是主流的防御手段。系统启动时生成随机密钥种子，哈希函数变为：

```text
H = f(Key, Random_Secret)
```

攻击者无法获知当前随机种子，因此也就难以构造针对性的碰撞数据。SipHash 是用于防御哈希洪水攻击的典型带密钥哈希函数，但具体运行时也可能使用其他随机化哈希算法。

在现代 .NET 中，`string.GetHashCode()` 和 `System.HashCode` 使用了进程级随机化机制，使相同数据在不同进程中产生的哈希码可能不一致。`object.GetHashCode()` 是可重写的虚方法，具体行为取决于运行时类型，不能认为所有实现都使用了相同的随机种子。无论采用哪种实现，运行时哈希码都不适合持久化或用于跨进程数据比对，相关说明见 [`object.GetHashCode()`](../DotNet/object.GetHashCode().md)。

### 链表转平衡树

**适用场景：** 语言或框架原生支持

部分哈希表会在某个槽位的链表长度超过阈值时，自动将链表转换为红黑树（自平衡二叉搜索树）。这不是所有哈希表的通用行为，具体阈值取决于语言和框架实现。

以 Java 8 及后续版本的 `HashMap` 为例：

- 当槽位中的元素较少时，使用链表存储。
- 当槽位中的节点数达到 `TREEIFY_THRESHOLD`（默认值为 8），并且哈希表容量达到 `MIN_TREEIFY_CAPACITY`（默认值为 64）时，将链表转换为红黑树。
- 如果节点数达到树化阈值，但哈希表容量仍小于 64，则优先扩容，而不是直接转换为红黑树。

这样，单个元素在冲突情况下的查询时间复杂度会从 `O(n)` 改善为 `O(log n)`，对多个碰撞元素进行操作时，最坏运行时间可以从 `O(n²)` 改善为 `O(n log n)`。

为什么要设置“8 个元素”（`TREEIFY_THRESHOLD`）的阈值限制？因为平衡树相比链表有着更高的开销，以及更散乱的内存布局（影响缓存命中率）。在正常情况下，哈希表的一个槽位通常只会存储少量元素，所以没有必要专门创建平衡树来存储冲突元素；对一些性能敏感的应用来说，这会造成显著的负面影响。

### 请求参数数量限制

**适用场景：** HTTP API 网关

在 API 网关或者应用入口处限制单个 HTTP 请求允许携带的最大参数数量，这样攻击者一次性发送大量参数时，请求在进入哈希表前就会被拒绝。

除了参数数量，还可以限制单个键和值的长度、请求体大小以及 JSON 嵌套深度，避免攻击者绕过单一维度的限制。

### IP 限流与黑名单

**适用场景：** 外部公开服务

对短时间内发送大量极端冲突请求的 IP 地址实施限流或拉黑措施，阻断攻击源。

IP 限流与黑名单只能作为辅助措施。攻击请求可能来自代理池或多个分布式节点，因此还需要结合请求参数限制、身份或租户维度的限流，以及服务端超时和资源上限共同防护。
