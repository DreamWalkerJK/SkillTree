# 哈希洪水攻击：原理、风险与防御（Hash Flooding Attack）

哈希洪水攻击也称**哈希冲突拒绝服务攻击**（Hash DoS），是一类算法复杂度拒绝服务攻击。攻击者向服务提交大量可控的键，使它们集中落入哈希表的少数桶（极端情况下是同一个桶），从而把原本接近常数时间的操作推向线性甚至平方级，消耗服务端的 CPU、内存和请求处理线程。

本文讨论的是哈希表的**桶碰撞**，不是密码学哈希的碰撞伪造。两者都源于多对一映射，但攻击目标、复杂度和防御方式不同；概念边界可参考[哈希碰撞](../Algorithm/哈希碰撞.md)和[生日攻击](../Cryptography/生日攻击.md)。

## 概念与威胁模型

哈希表先计算键的哈希码，再把哈希码映射到容量为 `m` 的桶下标。理想情况下，键均匀分布，查找、插入和删除的**期望**复杂度接近 `O(1)`；但这是建立在输入分布正常、负载受控和冲突处理得当的前提上。

攻击者关注的是最坏情况：如果 `n` 个不同键都落入同一桶，采用链地址法的桶会退化成长链表。查找和删除可能从 `O(1)` 退化到 `O(n)`；若每次插入都需要遍历确认键是否已存在，连续插入的总工作量可能达到 `O(n²)`。具体复杂度取决于实现（例如头插入可以让单次插入保持 `O(1)`），但 CPU、缓存和内存分配开销都会显著增加。

> [!WARNING]
> 哈希洪水攻击的危险在于“输入可控 + 处理成本随碰撞增长”，并不要求攻击流量本身很大。单个请求携带成千上万个参数，就可能在解析阶段触发问题。

## 攻击原理

### 1. 让输入进入同一冲突簇

攻击者需要找到一批不同的键，使哈希表的桶索引相同或高度集中。常见入口包括：

- HTTP 查询字符串、表单字段或 JSON 对象的键；
- 由应用转换为字典、集合或路由表的用户输入；
- 批量导入、搜索过滤器和协议头等键值集合。

历史上，一些语言和 Web 框架使用公开且可预测的哈希函数。攻击者可以离线准备冲突键，在请求到达服务端后迫使参数解析器、字典或集合执行大量比较。

### 2. 放大单次操作成本

链地址法会在同一桶中保存多个条目；开放寻址法则会形成很长的探测簇。随着冲突数量增加：

1. 比较键的次数增加，查找从期望 `O(1)` 变为 `O(n)`；
2. 插入、扩容和再散列需要处理更多条目；
3. CPU 缓存局部性变差，垃圾回收和内存分配压力上升；
4. 请求处理时间变长，线程池、连接池和队列逐步耗尽。

因此，少量恶意请求也可能拖慢整个进程，表现为延迟飙升、超时和可用性下降。

## 实施条件与影响

### 必要条件

成功的哈希洪水攻击通常同时具备以下条件：

1. **键由攻击者控制**：服务端会把输入键放入哈希表或等价的数据结构；
2. **输入数量或大小缺少上限**：请求可以携带大量参数、字段或集合成员；
3. **哈希行为可预测**：哈希函数、桶映射或随机种子容易推断，或者实现对恶意输入缺少最坏情况保护。

随机种子会显著提高构造针对性冲突的难度，但不能代替请求大小限制和限流；攻击者仍可能通过大量随机输入制造普通碰撞和资源压力。

### 典型影响

- 参数解析、反序列化或路由匹配耗时异常；
- CPU 使用率持续升高，P99/P999 延迟恶化；
- 工作线程、连接池或消息消费能力耗尽；
- 扩容只能暂时缓解，流量持续时会扩大基础设施成本。

## 为什么“换一个更好的哈希算法”仍不够

只要哈希输出空间有限，碰撞就无法从数学上被完全消除。对均匀随机的哈希值，碰撞概率可用生日问题近似：当输出空间为 `m`、计算次数为 `n` 时，至少一次碰撞的概率约为

```text
P(collision) ≈ 1 - exp(-n(n - 1) / (2m))
```

例如取值空间为 365 时，随机取约 23 个值，发生任意两值相同的概率就超过 50%；取约 60 个值时超过 99%。这说明“随机碰撞迟早会发生”，但不等于攻击者一定能构造出**指定**的冲突键。

哈希洪水攻击利用的是可预测性和最坏情况成本。更长的输出或更复杂的非密钥哈希只能降低随机碰撞概率；若攻击者能分析算法并离线构造输入，仍可能发起定向攻击。真正有效的思路是让哈希结果依赖服务端保密的随机种子，并限制每个请求能够触发的工作量。

## 防御策略

### 1. 使用带密钥哈希或进程级随机种子

为哈希函数加入每次进程启动时生成的随机秘密，使其形如 `H = f(key, secret)`。攻击者不知道当前秘密，就难以预先构造定向冲突。

- 对需要抗对抗性输入的哈希表，可选用 SipHash 等专门的带密钥哈希；
- 使用语言或框架提供的随机化字符串哈希和安全集合实现；
- 秘密种子不得通过日志、错误信息或接口返回值泄露；
- 带密钥哈希用于数据结构防护，不等同于数字签名或消息完整性校验。

### 2. 采用有界的冲突处理

在链表过长时切换到更稳定的结构，可以把单次查找的最坏复杂度从 `O(n)` 降为 `O(log n)`。例如 Java 8 的 `HashMap` 在满足容量等条件且桶长度达到阈值时会树化为红黑树；阈值是该实现的工程参数，不是所有语言的通用默认值。树化会增加节点开销，因此仍应配合随机化和输入限制。

对于开放寻址表，应设置合理的负载因子、探测上限和扩容策略，避免无限制探测。任何冲突处理方案都需要通过压测验证最坏情况，而不能只看平均吞吐量。

### 3. 限制请求参数与解析工作量

在网关、反向代理和应用入口同时设置上限：

- 单请求的参数/字段数量；
- 单个键和值的长度、请求体大小和嵌套深度；
- 分页、过滤器和批量操作的最大元素数；
- 解析或业务处理的超时预算。

尽量在进入哈希表、反序列化器或业务逻辑前拒绝超限请求，并返回明确但不过度暴露实现细节的错误。

### 4. 限流、WAF 与资源隔离

对短时间内重复发送大参数请求的来源实施令牌桶/漏桶限流，并在边缘层丢弃明显异常的请求。IP 黑名单只能作为辅助措施：攻击可能来自代理池或僵尸网络，不能把单一 IP 规则当作唯一防线。

将高成本解析、批量导入等功能与核心请求线程池隔离，设置并发上限和队列长度，避免一个接口拖垮整个进程。

### 5. 监控与回归测试

建议记录请求大小、参数数量、解析耗时、拒绝原因和按接口/租户划分的资源消耗；对延迟分位数和线程池队列设置告警。测试时至少覆盖：

- 正常分布的大量键；
- 大量随机键；
- 同桶或高集中度键（使用测试桩或内部生成器，不在生产环境构造攻击流量）；
- 超过参数、深度、大小和超时阈值的请求。

## .NET 工程注意事项

`.NET` 的 `string.GetHashCode()`、`object.GetHashCode()` 和 `System.HashCode` 主要服务于当前进程内的哈希集合定位，不适合作为持久化 ID、跨进程协议字段或安全校验值。运行时会使用进程级随机化，使相同输入在不同进程中可能得到不同哈希码，这也提高了针对性哈希洪水攻击的门槛。详见[object.GetHashCode()](../DotNet/object.GetHashCode().md)。

工程上应遵循以下原则：

- 不依赖哈希码的稳定数值进行跨进程比较或持久化；
- 对外部键使用框架默认的安全比较器，避免自行实现可预测哈希；
- 对 `Dictionary`、`HashSet` 和模型绑定参数设置数量、长度和超时限制；
- 需要完整性或身份认证时使用标准 HMAC/KMAC 等机制，而不是 `GetHashCode()`。

## 排查与验证清单

发现疑似攻击时，可按以下顺序检查：

1. 是否存在单请求参数数量、键长度和请求体大小上限；
2. 延迟增加是否集中在参数解析、反序列化或字典构建阶段；
3. 当前运行时和集合实现是否启用了哈希随机化或最坏情况保护；
4. 是否有异常的重复键模式、来源分布和请求大小；
5. 限流、超时和隔离策略能否在不影响正常流量的情况下生效；
6. 通过受控压测验证修复前后的 P95/P99 延迟、CPU 和内存曲线。

## 总结

哈希洪水攻击不是“哈希函数一定不安全”，而是利用了可控输入与数据结构最坏情况之间的组合风险。稳妥的防线应分层建设：使用带密钥的随机化哈希降低可预测性，使用有界冲突处理控制单次成本，在入口限制参数和解析工作量，再辅以限流、隔离、监控和回归测试。任何单一措施都不能替代完整的资源保护策略。
