# 状态机：形式化模型、执行语义与工程实践

状态机（State Machine）是对离散事件驱动系统行为的建模方法：系统保留一个当前控制状态，在事件到达时根据状态、守卫条件和扩展数据选择转移，执行相应动作并进入后继状态。它适合描述协议会话、设备控制、订单生命周期、用户界面、工作流和编译器等「未来行为取决于当前阶段」的问题。

> [!NOTE]
> 「状态机」是一个模型家族，不是单一类型。理论计算机科学中的确定有限自动机（DFA）、控制系统中的 Moore/Mealy 机、工程中的扩展有限状态机（EFSM）、UML State Machine/Statecharts，以及 GoF 状态模式解决的问题并不相同。

## 1. 状态机解决什么问题

### 1.1 状态是对历史的有限摘要

「状态」不只是一个字段值，而是系统为了决定未来行为而保留的、与过往交互有关的控制信息。若两段不同历史在面对所有未来事件时都应产生相同行为，它们可被抽象为同一状态。

例如，「订单是否可发货」取决于它是否已支付，而通常不取决于用户在创建订单前浏览过哪些页面。「已支付」是必要的控制状态，浏览历史则不应进入该状态机。

### 1.2 适用特征

当问题具有以下特征时，状态机通常比分散的条件语句更容易推理：

- 系统的行为是离散事件驱动的。
- 同一事件在不同生命周期阶段的含义不同。
- 合法转移有明确约束，非法组合必须被阻止。
- 需要对超时、重试、故障、取消或恢复进行显式建模。
- 需要生成状态图、审计轨迹，或验证「永远不进入某状态」等性质。

常见信号是代码中出现了大量与当前阶段有关的 `if/else`、多个本应互斥的布尔字段，或者状态修改分散在 Controller、任务、SQL 和消息消费者中。

### 1.3 核心收益与代价

| 收益                               | 代价                                               |
| ---------------------------------- | -------------------------------------------------- |
| 明确合法状态与转移边界             | 需要定义事件、语义和非法输入策略                   |
| 将控制流转化为可视化、可分析的图   | 状态和数据边界划分不当会造成状态爆炸               |
| 便于覆盖超时、重复、乱序和失败路径 | 引入层次、并发区域和历史状态后执行语义会明显变复杂 |
| 能够系统地做转移覆盖和不变量测试   | 持久化、并发控制和外部副作用仍需要额外工程机制     |

状态机能暴露复杂性，不能消除问题本身的复杂性。

## 2. 概念边界与模型谱系

| 模型                            | 典型形式                                                     | 核心语义                                                  | 典型用途                 |
| ------------------------------- | ------------------------------------------------------------ | --------------------------------------------------------- | ------------------------ |
| 确定有限自动机（DFA）           | $M=(Q,\Sigma,\delta,q_0,F)$                                | 对输入串进行接受/拒绝；每个「状态—符号」对有唯一后继状态 | 词法分析、正则语言       |
| 非确定有限自动机（NFA）         | $\delta:Q\times(\Sigma\cup\{\varepsilon\})\rightarrow 2^Q$ | 同一输入可有多个后继状态                                  | 正则语言建模             |
| 标号转换系统（LTS）             | $(S,Act,\rightarrow,I)$                                    | 关注可达配置和行为轨迹，终止/接受状态不是必需成分         | 协议、并发系统与模型检查 |
| Moore/Mealy 机                  | 在转移系统上增加输出函数                                     | 建模输入、控制状态与输出之间的关系                        | 数字电路、控制器、协议   |
| 扩展有限状态机（EFSM）          | 有限控制状态 + 数据 + 守卫 + 动作                            | 用扩展数据避免将每个数值展开为状态                        | 业务流程、设备控制       |
| UML State Machine / Statecharts | 层次、正交区域、历史与完成语义                               | 用结构化状态管理复杂反应式行为                            | 大型软件与系统建模       |
| GoF State Pattern               | Context + 多个 State 对象                                    | 用多态组织与状态有关的行为                                | 面向对象实现技术         |

需特别注意以下边界：

- DFA 是一种语言接受器；工程状态机通常不需要接受状态集 $F$，而且转移常为偏函数。
- 「有限」一般指有限的控制状态。如果 EFSM 的扩展数据可为任意长字符串、无界整数或任意集合，完整配置空间并不是有限集。
- GoF 状态模式可以实现状态机，但它本身不保证有限性、确定性、事件队列语义、转移完备性或可验证性。
- 业务实体的「状态字段」也不自动构成状态机；还需要明确事件、合法转移、守卫和非法输入策略。

## 3. 基础形式化模型

一个实用的扩展状态机可抽象为：

$$
M=(S,s_0,E,X,T)
$$

其中：

- $S$ 是有限控制状态集合；
- $s_0\in S$ 是初始状态；
- $E$ 是事件集合；
- $X$ 是扩展状态变量集合；
- $T$ 是转移集合。

一条转移可记为：

$$
t=(s,e,g,a,s')
$$

它表示：机器处于源状态 $s$，收到事件 $e$，且守卫 $g$ 为真时，执行动作 $a$ 并进入目标状态 $s'$。当前完整配置为 $c=(s,\nu)$，$\nu$ 是扩展变量的当前赋值。

### 3.1 状态、事件、守卫和动作

| 元素                       | 定义                         | 建模要求                                     |
| -------------------------- | ---------------------------- | -------------------------------------------- |
| 状态（State）              | 影响后续行为的持久控制阶段   | 应用领域语言命名，不应与临时计算步骤混淆     |
| 事件（Event）              | 已经发生、可能触发转移的事实 | 应包含必要载荷，并与命令意图区分             |
| 守卫（Guard）              | 当转移可被选择的布尔条件     | 应为无副作用的纯判断，不执行 I/O，不修改模型 |
| 动作/效果（Action/Effect） | 转移被选中后的计算或外部影响 | 内部数据更新与不可回滚的外部副作用应显式区分 |

事件表示已发生的事实，例如 `PaymentSucceeded`；命令表示希望执行的意图，例如 `RequestPayment`。在异步系统中，发出命令不等于相应事件已经成立。

### 3.2 确定性

对于任意当前配置和事件，至多应有一条最终被选中的转移；或者规范必须定义完整、稳定的优先级规则。如果同一「源状态—事件」下的多个守卫可同时为真，又没有明确优先级，实现结果就取决于容器遍历或注册顺序，这是隐性非确定性。

任意程序表达式之间是否互斥，通常无法由通用工具完整判定。高保证系统应限制守卫语言、明确分区条件，或对可能重叠的区域做模型检查。

### 3.3 完备性与非法事件

每个与业务有关的「状态—事件」组合都应被归入一种显式策略：

1. 进行状态转移。
2. 执行内部动作但不离开当前状态。
3. 幂等忽略，并记录原因。
4. 延迟到其他状态再处理。
5. 拒绝并返回可诊断错误。

不应让「没有 `case`」或「字典查不到」偶然成为系统语义。

### 3.4 不变量

状态机的价值不只在于「能跳到哪里」，更在于保护任意可达配置都必须满足的不变量。例如：

$$
state=Shipped \Rightarrow paidAt\neq null
$$

$$
state=Cancelled \Rightarrow shippedAt=null
$$

每条转移都应在前置不变量成立的条件下，产生仍满足不变量的新配置。

## 4. Moore 机、Mealy 机与动作语义

### 4.1 Moore 机

Moore 机的输出只由当前状态决定：

$$
\lambda:S\rightarrow O
$$

例如设备处于 `Alarm` 状态时持续点亮红灯，这类「状态被激活时持续呈现」的输出更接近 Moore 语义。

### 4.2 Mealy 机

Mealy 机的输出由当前状态和本次输入共同决定：

$$
\lambda:S\times I\rightarrow O
$$

例如处于 `AwaitingPayment` 时收到 `Cancel`，产生一次 `ReleaseInventory` 效果，更接近 Mealy 语义。

Mealy 建模有时能使用更少状态，Moore 输出的边界往往更稳定；但这不是无条件的性能优劣结论，应按语义和可验证性选择。

### 4.3 UML 状态机的混合动作

UML State Machine 同时支持：

- `entry`：进入状态时执行。
- `exit`：退出状态时执行。
- `doActivity`：状态激活期间的持续活动。
- 转移效果：某条转移被选中时执行。

因此，UML 状态机不应被简单归类为纯 Moore 或纯 Mealy 机。

## 5. 状态图与执行语义

### 5.1 转移标记

UML 中常用的转移标记为：

```text
源状态 -- 事件 [守卫] / 转移效果 --> 目标状态
```

一个订单片段可用文本图表示为：

```text
                         PaymentFailed [canRetry]
                        +-------------------------+
                        |                         |
                        v                         |
[*] -- Submit --> AwaitingPayment -- PaymentSucceeded --> Paid -- Ship --> Shipped
                        |
                        +-- Cancel / ReleaseInventory --> Cancelled
                        |
                        +-- PaymentFailed [!canRetry] --> Cancelled
```

图不能只标注箭头；事件载荷、守卫、副作用、自转移语义和非法事件策略应在模型或陪同规格中定义。

### 5.2 外部自转移与内部转移

目标状态与源状态名称相同，不代表执行语义必然相同：

- **外部自转移**通常退出后重新进入同一状态，因此会再次执行 `exit` 和 `entry`。
- **内部转移**处理事件但不退出状态，不重启该状态的进入/退出动作。

不同库的 API 默认值可能不同，选型时必须核对，不能从方法名猜测。

### 5.3 Run-to-completion

UML 的 run-to-completion（RTC）原则表示：开始处理一个事件后，本次响应所需的状态转移必须完成，然后才能分派下一个事件。这是状态机分派层面的串行语义，不等于：

- 整个业务流程是一个数据库事务。
- 外部网络调用与状态更新具有原子性。
- 状态机自动具备多线程安全性。

对于一般的平面状态机，一个微步可理解为：

1. 选择一条启用的转移；存在正交区域时，可为一组互不冲突的转移。
2. 执行相关状态的退出动作。
3. 执行转移效果。
4. 执行目标状态的进入动作。
5. 到达新稳定配置。

在层次状态中，退出通常从内向外，进入从外向内，路径由源和目标的最低公共祖先决定。

### 5.4 宏步、微步与事件队列

W3C SCXML 给出了比「调一次 `Handle`」更完整的解释器语义：

- 一个外部事件启动一个宏步（macrostep）。
- 宏步可包含多个微步（microstep）。
- 内部事件与无事件转移可继续驱动微步。
- 直到内部队列为空且没有无事件转移可执行，机器才达到稳定配置并处理下一个外部事件。

动作中产生的新事件应入队，而不应递归调用 `Dispatch`。递归分派会导致重入、调用栈增长，并可能让新事件越过当前转移的收尾动作。

事件队列契约至少应声明：

- FIFO 是全局的还是仅对单个生产者成立。
- 队列容量、溢出策略与背压方式。
- 未知事件、重复事件和乱序事件如何处理。
- 异常是否阻断后续事件，以及失败事件如何重试或移入死信。

长时间 I/O 不应占用 RTC 循环。更稳健的结构是：转移产生「效果命令」，由外部执行器完成 I/O，然后投递成功、失败或超时事件。

## 6. 复合状态、并发区域与历史状态

### 6.1 层次状态

复合状态可将共享行为提取到父状态。例如 `Operational` 包含 `Idle`、`Running`、`Paused` 三个子状态，`PowerOff` 转移可只定义在 `Operational` 上，不必在每个子状态重复。

层次状态机的关键语义包括：

- 复合 OR 状态激活时，其直接子状态中通常恰有一个激活。
- 复合状态应定义默认初始子状态。
- 转移选择通常从激活叶子状态向祖先查找，但精确冲突规则应以所采用的 UML、SCXML 或引擎规范为准。
- 层次化减少了图与规则的重复，但不会凭空消除底层状态空间。

### 6.2 正交区域

正交（AND）状态的多个区域同时激活。此时当前状态不再是一个枚举值，而是一个合法激活配置集合。

正交区域描述逻辑并发，不代表每个区域都在独立线程上运行，也不自动提供线程安全。若 $k$ 个独立区域的状态数分别为 $n_1,\ldots,n_k$，展开后的组合上界可达：

$$
\prod_{i=1}^{k}n_i
$$

因此，正交区域能避免在图上手工穷举组合，但验证时仍要面对状态爆炸。

### 6.3 历史状态

- **浅历史**恢复复合状态上次激活的直接子状态。
- **深历史**恢复上次激活的完整嵌套后代配置。

在尚无历史记录的第一次进入中，必须定义默认目标。历史伪状态只用于恢复活动配置，不是审计日志，不能替代持久化的状态变更记录。

### 6.4 完成与无事件转移

子状态进入 final 后可使父状态产生完成语义。无事件转移可在一个宏步中连续触发，因此必须检测无事件环；否则机器可能永远无法回到外部事件队列，形成活锁。

## 7. 设计方法

### 7.1 从场景与不变量出发

1. 确定状态机边界，为哪个实体、会话或设备实例维护状态。
2. 使用业务事实列出事件，包括成功、失败、取消、超时、重复与过期场景。
3. 识别决定未来合法行为的持久阶段，而不是把每个函数步骤都命名为状态。
4. 先写不变量和非法轨迹，再补全正常路径。
5. 建立转移表，对每个状态—事件对标记转移、忽略、延迟或拒绝。

状态应回答「系统现在处于哪个行为阶段」，扩展数据应回答「该阶段所需的参数是什么」。例如将每个重试次数建模为 `Retry0`、`Retry1`、`Retry2` 往往不如 `AwaitingPayment + RetryCount` 清晰。

### 7.2 状态分解的判断标准

应增加一个状态，当且仅当它至少带来一项可观察差异：

- 合法事件集合不同。
- 对同一事件的响应不同。
- 不变量不同。
- 需要独立超时、入口/退出动作或持久化恢复语义。
- 运维或用户需要对该阶段进行独立观测和介入。

反之，只有显示文本、临时局部值或相同规则下的细微数据差异，通常应留在扩展数据中。

### 7.3 时间建模

超时不是「后台定时任务顺便改一下字段」，而应被建模为显式事件，例如 `PaymentTimedOut(attemptId)`。启动定时器时应绑定状态实例或 epoch；即使机器已经离开并重新进入同名状态，旧超时事件也必须能被识别为过期。

### 7.4 转移表作为可执行规格

以订单为例：

| 源状态                    | 事件             | 守卫                     | 目标状态        | 效果                   |
| ------------------------- | ---------------- | ------------------------ | --------------- | ---------------------- |
| Created                   | Submit           | 订单有商品               | AwaitingPayment | 请求支付、启动超时计时 |
| AwaitingPayment           | PaymentSucceeded | 支付尝试号与当前尝试一致 | Paid            | 记录支付、取消超时     |
| AwaitingPayment           | PaymentFailed    | 仍可重试                 | AwaitingPayment | 开始新支付尝试         |
| AwaitingPayment           | PaymentFailed    | 不可重试                 | Cancelled       | 释放库存               |
| Paid                      | Ship             | 物流单号有效             | Shipped         | 发布已发货事件         |
| Created / AwaitingPayment | Cancel           | 无                       | Cancelled       | 释放库存               |

如果转移表与代码分别维护，它们终将漂移。表驱动实现可直接从同一规格生成状态图、覆盖率数据和基础测试用例。

## 8. 工程实现策略与选型

### 8.1 枚举与 `switch`

```csharp
switch ((state, eventType))
{
    case (OrderState.Created, EventType.Submit):
        return OrderState.AwaitingPayment;
    case (OrderState.Paid, EventType.Ship):
        return OrderState.Shipped;
    default:
        throw new InvalidTransitionException(state, eventType);
}
```

适合状态、事件和拓扑都较小且稳定的机器。优点是控制流直观、调试成本低；缺点是状态—事件矩阵扩大后会形成巨型分支，守卫、动作和错误策略容易散落。

### 8.2 表驱动状态机

以 `(state, event)` 为键存储候选转移，每条转移包含目标、守卫和动作。优点是拓扑集中、容易检查重复转移、生成图和统计覆盖率。

- 稠密二维表的空间为 $O(|S||E|)$。
- 稀疏字典的空间接近 $O(|T|)$。

表驱动并不天然比 `switch` 快。选择它的主要理由是可维护性、可分析性和动态配置需求，性能应在目标平台上测量。

### 8.3 函数/委托分派

每个状态对应一个函数或 C# delegate，适合嵌入式与轻量框架。它能拆分状态行为，但如果每个处理函数内部自行修改状态和执行 I/O，全局转移图依然会被分散。

### 8.4 State Pattern

每个状态对象封装状态相关行为，适合行为复杂、每个状态依赖不同服务的面向对象系统。它用多态取代条件分支，但代价是转移图分散在多个类中，生成全局图和执行静态检查更困难。

### 8.5 状态机引擎或代码生成

出现以下需求时，应优先评估成熟引擎或从模型生成代码：

- 层次状态、正交区域、历史状态或延迟事件。
- 状态持久化、分布式调度和长时间工作流。
- 由图形模型生成代码、文档或测试的需求。
- 对 SCXML 等标准的互操作性需求。

引擎选型不能只比较 API 美观程度；必须确认自转移、守卫冲突、事件队列、异常、线程安全、持久化与升级语义。

### 8.6 选型对比

| 方案                  | 适用条件                    | 主要优点               | 主要风险                   |
| --------------------- | --------------------------- | ---------------------- | -------------------------- |
| `switch` / 模式匹配 | 小型、拓扑稳定              | 直观、无额外抽象       | 分支膨胀、矩阵不完备       |
| 表驱动                | 中等复杂度、需要生成图/校验 | 拓扑集中、可分析       | 复杂行为委托可降低可读性   |
| 函数/委托分派         | 行为需拆分、资源受限        | 轻量、便于单独测试     | 转移图可能分散             |
| State Pattern         | 各状态行为复杂、依赖差异大  | 多态封装、单个状态内聚 | 类数量增长、全局拓扑不直观 |
| 引擎/代码生成         | 层次、并发、持久化、可视化  | 语义完整、工具支持     | 学习与运维成本、语义锁定   |

## 9. C# 示例：可验证的订单状态机

下列示例使用稀疏转移表，演示：

- 合法与非法转移。
- 无副作用守卫。
- 多条候选转移的确定性检查。
- 过期支付回调的幂等忽略。
- 内部模型更新与外部效果分离。
- 单线程 FIFO 队列防止递归重入。

### 9.1 模型、事件与效果

using System;
using System.Collections.Generic;
using System.Collections.Immutable;
using System.Linq;

public enum OrderState
{
    Created,
    AwaitingPayment,
    Paid,
    Shipped,
    Cancelled
}

public abstract record OrderEvent(Guid EventId);

public sealed record Submit(Guid EventId) : OrderEvent(EventId);

public sealed record PaymentSucceeded(
    Guid EventId,
    Guid AttemptId,
    DateTimeOffset PaidAt) : OrderEvent(EventId);

public sealed record PaymentFailed(
    Guid EventId,
    Guid AttemptId,
    string Reason) : OrderEvent(EventId);

public sealed record Ship(
    Guid EventId,
    string TrackingNumber,
    DateTimeOffset ShippedAt) : OrderEvent(EventId);

public sealed record RequestPayment(
    Guid OrderId,
    Guid AttemptId) : OrderEffect;

public sealed record ReleaseInventory(
    Guid OrderId,
    string Reason) : OrderEffect;

    Guid OrderId,
    string TrackingNumber) : OrderEffect;

public sealed record OrderModel(
    Guid Id,
    OrderState State,
    int ItemCount,
    Guid? ActivePaymentAttemptId = null,

    DateTimeOffset? PaidAt = null,
    DateTimeOffset? ShippedAt = null,

### 9.2 转移规则与解释器

```csharp
public delegate bool Guard(OrderModel model, OrderEvent @event);

public delegate TransitionResult Reducer(
    OrderModel model,
    OrderEvent @event);

public sealed record TransitionRule(
    OrderState Source,
    Type EventType,
    Guard Guard,
    Reducer Reduce,
    string Name);

public sealed class OrderStateMachine
{
    private const int MaximumPaymentFailures = 3;

    private readonly IReadOnlyDictionary<
        (OrderState State, Type EventType),
        ImmutableArray<TransitionRule>> _rules;

    public OrderStateMachine()
    {
        var rules = new[]
        {
            Rule<Submit>(
                "submit-non-empty-order",
                OrderState.Created,
                (model, _) => model.ItemCount > 0,
                (model, _) =>
                {
                    var attemptId = Guid.NewGuid();
                    var next = model with
                    {
                        State = OrderState.AwaitingPayment,
                        ActivePaymentAttemptId = attemptId
                    };

                    return Accepted(
                        next,
                        new RequestPayment(model.Id, attemptId));
                }),

            Rule<PaymentSucceeded>(
                "accept-current-payment",
                OrderState.AwaitingPayment,
                IsCurrentAttempt,
                (model, @event) => Accepted(model with
                {
                    State = OrderState.Paid,
                    PaidAt = @event.PaidAt,
                    ActivePaymentAttemptId = null
                })),

            Rule<PaymentFailed>(
                "retry-current-payment",
                OrderState.AwaitingPayment,
                (model, @event) =>
                    IsCurrentAttempt(model, @event) &&
                    model.PaymentFailures + 1 < MaximumPaymentFailures,
                (model, _) =>
                {
                    var attemptId = Guid.NewGuid();
                    var next = model with
                    {
                        PaymentFailures = model.PaymentFailures + 1,
                        ActivePaymentAttemptId = attemptId
                    };

                    return Accepted(
                        next,
                        new RequestPayment(model.Id, attemptId));
                }),

            Rule<PaymentFailed>(
                "cancel-after-last-payment-failure",
                OrderState.AwaitingPayment,
                (model, @event) =>
                    IsCurrentAttempt(model, @event) &&
                    model.PaymentFailures + 1 >= MaximumPaymentFailures,
                (model, @event) => Accepted(
                    model with
                    {
                        State = OrderState.Cancelled,
                        PaymentFailures = model.PaymentFailures + 1,
                        ActivePaymentAttemptId = null
                    },
                    new ReleaseInventory(model.Id, @event.Reason))),

            Rule<Cancel>(
                "cancel-created-order",
                OrderState.Created,
                (_, _) => true,
                (model, @event) => Accepted(
                    model with { State = OrderState.Cancelled },
                    new ReleaseInventory(model.Id, @event.Reason))),

            Rule<Cancel>(
                "cancel-awaiting-order",
                OrderState.AwaitingPayment,
                (_, _) => true,
                (model, @event) => Accepted(
                    model with
                    {
                        State = OrderState.Cancelled,
                        ActivePaymentAttemptId = null
                    },
                    new ReleaseInventory(model.Id, @event.Reason))),

            Rule<Ship>(
                "ship-paid-order",
                OrderState.Paid,
                (_, @event) =>
                    !string.IsNullOrWhiteSpace(@event.TrackingNumber),
                (model, @event) => Accepted(
                    model with
                    {
                        State = OrderState.Shipped,
                        ShippedAt = @event.ShippedAt,
                        TrackingNumber = @event.TrackingNumber
                    },
                    new PublishOrderShipped(
                        model.Id,
                        @event.TrackingNumber)))
        };

        _rules = rules
            .GroupBy(rule => (rule.Source, rule.EventType))
            .ToDictionary(
                group => group.Key,
                group => group.ToImmutableArray());
    }

    public TransitionResult Dispatch(
        OrderModel model,
        OrderEvent @event)
    {
        if (model.ProcessedEvents.Contains(@event.EventId))
        {
            return new TransitionResult(
                model,
                ImmutableArray<OrderEffect>.Empty,
                Ignored: true,
                Reason: "duplicate-event");
        }

        // 延迟到达的旧支付结果是已知可能情形，显式幂等忽略。
        if (@event is PaymentSucceeded succeeded &&
            model.State == OrderState.AwaitingPayment &&
            !IsCurrentAttempt(model, succeeded))
        {
            return IgnoreAndRemember(model, @event, "stale-payment-attempt");
        }

        if (@event is PaymentFailed failed &&
            model.State == OrderState.AwaitingPayment &&
            !IsCurrentAttempt(model, failed))
        {
            return IgnoreAndRemember(model, @event, "stale-payment-attempt");
        }

        var key = (model.State, @event.GetType());
        if (!_rules.TryGetValue(key, out var candidates))
        {
            throw new InvalidTransitionException(model.State, @event.GetType());
        }

        var enabled = candidates
            .Where(rule => rule.Guard(model, @event))
            .Take(2)
            .ToArray();

        if (enabled.Length == 0)
        {
            throw new InvalidTransitionException(model.State, @event.GetType());
        }

        if (enabled.Length > 1)
        {
            throw new AmbiguousTransitionException(
                model.State,
                @event.GetType());
        }

        var result = enabled[0].Reduce(model, @event);
        Validate(result.Model);

        return result with
        {
            Model = result.Model with
            {
                Version = model.Version + 1,
                ProcessedEventIds = model.ProcessedEvents.Add(@event.EventId)
            }
        };
    }

    private static TransitionRule Rule<TEvent>(
        string name,
        OrderState source,
        Func<OrderModel, TEvent, bool> guard,
        Func<OrderModel, TEvent, TransitionResult> reduce)
        where TEvent : OrderEvent
    {
        return new TransitionRule(
            source,
            typeof(TEvent),
            (model, @event) => guard(model, (TEvent)@event),
            (model, @event) => reduce(model, (TEvent)@event),
            name);
    }

    private static bool IsCurrentAttempt(
        OrderModel model,
        PaymentSucceeded @event) =>
        model.ActivePaymentAttemptId == @event.AttemptId;

    private static bool IsCurrentAttempt(
        OrderModel model,
        PaymentFailed @event) =>
        model.ActivePaymentAttemptId == @event.AttemptId;

    private static TransitionResult Accepted(
        OrderModel model,
        params OrderEffect[] effects) =>
        new(model, effects.ToImmutableArray());

    private static TransitionResult IgnoreAndRemember(
        OrderModel model,
        OrderEvent @event,
        string reason)
    {
        var ignored = model with
        {
            Version = model.Version + 1,
            ProcessedEventIds =
                model.ProcessedEvents.Add(@event.EventId)
        };

        Validate(ignored);

        return new TransitionResult(
            ignored,
            ImmutableArray<OrderEffect>.Empty,
            Ignored: true,
            Reason: reason);
    }

    private static void Validate(OrderModel model)
    {
        if (model.State == OrderState.Paid && model.PaidAt is null)
        {
            throw new InvalidOperationException(
                "A paid order must have PaidAt.");
        }

        if (model.State == OrderState.Shipped &&
            (model.PaidAt is null ||
             model.ShippedAt is null ||
             string.IsNullOrWhiteSpace(model.TrackingNumber)))
        {
            throw new InvalidOperationException(
                "A shipped order must contain payment and shipment data.");
        }

        if (model.State == OrderState.Cancelled &&
            model.ShippedAt is not null)
        {
            throw new InvalidOperationException(
                "A cancelled order cannot be shipped.");
        }
    }
}
```

`Reducer` 修改内部模型并返回 `OrderEffect`，但不直接调用支付、库存或消息系统。这使得转移可快速重放和单元测试，也为应用层使用事务性 Outbox 留出边界。

`Guid.NewGuid()` 在教学示例中用于创建支付尝试号。若要进行完全确定的重放，应将 ID 生成器作为输入，或将新 ID 与状态变更一起持久化。

过期事件虽然不改变业务状态，但示例会把其 ID 加入去重集，因此仍是一次需持久化的模型修改，并递增 `Version`。如果去重状态保存在独立 Inbox，则可保持聚合版本不变。

示例中的 `ProcessedEventIds` 用于说明幂等语义，不应在长生命期实例内无界增长。生产系统应根据业务时间窗选择 Inbox/去重表、有界缓存、单调序列号或稳定的业务幂等键，并定义清理策略。

### 9.3 避免重入的单线程运行器

```csharp
public sealed class OrderMachineRunner
{
    private readonly OrderStateMachine _machine;
    private readonly Queue<OrderEvent> _queue = new();
    private bool _processing;

    public OrderMachineRunner(
        OrderStateMachine machine,
        OrderModel initialModel)
    {
        _machine = machine;
        Model = initialModel;
    }

    public OrderModel Model { get; private set; }

    public event Action<OrderEffect>? EffectProduced;

    public void Post(OrderEvent @event)
    {
        _queue.Enqueue(@event);

        if (_processing)
        {
            return;
        }

        _processing = true;
        try
        {
            while (_queue.TryDequeue(out var nextEvent))
            {
                var result = _machine.Dispatch(Model, nextEvent);
                Model = result.Model;

                foreach (var effect in result.Effects)
                {
                    EffectProduced?.Invoke(effect);
                }
            }
        }
        finally
        {
            _processing = false;
        }
    }
}
```

如果 `EffectProduced` 的订阅者立即调用 `Post`，新事件只会入队，不会递归进入正在执行的转移。

> [!WARNING]
> `Queue<T>` 和 `_processing` 只定义了单线程内的串行分派，不使整个运行器自动具备多线程安全性。多线程生产者应通过单消费者 Channel/Actor、锁或持久化队列实现明确的并发契约。

using System;
using Xunit;

public sealed class OrderStateMachineTests
{
    private readonly OrderStateMachine _machine = new();

    [Fact]
    public void Unpaid_order_cannot_be_shipped()
    {
        var order = NewOrder();

        Assert.Throws<InvalidTransitionException>(() =>

        Assert.Equal(OrderState.AwaitingPayment, result.Model.State);
        Assert.True(result.Model.Version > submitted.Version);
        Assert.Contains(staleEvent.EventId, result.Model.ProcessedEvents);
    }

    public void Paid_order_can_be_shipped_and_version_is_monotonic()

        var submitted = _machine.Dispatch(
            NewOrder(),
            new Submit(Guid.NewGuid())).Model;

        var paid = _machine.Dispatch(
            submitted,
            new PaymentSucceeded(
                Guid.NewGuid(),
                submitted.ActivePaymentAttemptId!.Value,
                DateTimeOffset.UtcNow)).Model;

        var shipped = _machine.Dispatch(
            paid,
            new Ship(
                Guid.NewGuid(),

                DateTimeOffset.UtcNow)).Model;

        Assert.Equal(OrderState.Shipped, shipped.State);
        Assert.NotNull(shipped.PaidAt);
        Assert.True(shipped.Version > paid.Version);
        Assert.True(paid.Version > submitted.Version);
    }

    [Fact]
    public void Duplicate_event_is_idempotently_ignored()
    {
        var submit = new Submit(Guid.NewGuid());
        var submitted = _machine.Dispatch(NewOrder(), submit).Model;

        var duplicate = _machine.Dispatch(submitted, submit);

        Assert.True(duplicate.Ignored);
        Assert.Equal("duplicate-event", duplicate.Reason);
        Assert.Same(submitted, duplicate.Model);
        Assert.Empty(duplicate.Effects);
    }

    [Fact]
    public void Cancelled_order_is_terminal()
    {
        var cancelled = _machine.Dispatch(
            NewOrder(),
            new Cancel(Guid.NewGuid(), "customer-request")).Model;

        Assert.Throws<InvalidTransitionException>(() =>
            _machine.Dispatch(cancelled, new Submit(Guid.NewGuid())));
    }

## 10. 测试、图分析与形式验证

### 10.1 结构校验

在运行测试之前，可对转移图做静态检查：

- 初始状态和所有转移目标都存在。
- 所有预期非终态都可从初态达到。
- 预期终态可达，且没有意外的吸收状态或孤立状态。
- 每个状态—事件对均已明确为处理、忽略、延迟或报错。
- 同一触发器下不存在未解决的守卫重叠或守卫空洞。
- 复合状态的 initial、final 和 history 目标合法。
- 不存在无守卫的无事件环。

对 EFSM 而言，不考虑守卫的图可达，不代表该状态在数据约束下语义可达。高风险系统可对数据做有界抽象，并使用 SMT 求解或模型检查工具。

### 10.2 转移测试

最小测试组合应包含：

- 每条转移至少一个正向用例。
- 每个守卫的真、假和边界值。
- 退出动作、转移效果、进入动作的顺序。
- 非法、未知、重复、过期和乱序事件。
- 自转移和内部转移的不同入口/退出行为。
- 转移效果发出新事件时的队列顺序。

可量化的覆盖指标包括：状态覆盖、转移覆盖、状态—事件对覆盖、守卫真/假覆盖，以及关键转移对或事件序列覆盖。

### 10.3 序列与属性测试

单条转移正确，不代表长序列正确。可使用属性测试生成事件序列，每一步都检查：

- 已发货订单必然已支付。
- 已取消订单不会再进入已支付或已发货。
- 版本号在每次已接受转移后严格递增。
- 重复或过期支付结果不改变当前业务状态。

模型驱动测试可将实际实现与一个纯函数参考模型对比，尤其适合验证框架配置、数据库实现和消息驱动运行器是否具有相同语义。

### 10.4 安全性与活性

- **安全性（safety）**：坏事永远不发生，例如「未支付订单永远不会发货」。
- **活性（liveness）**：在环境满足假设时，好事最终会发生，例如「支付成功且物流最终响应时，订单最终完成」。

活性结论必须明确环境假设，例如公平调度、消息不会永久丢失、外部服务最终响应、重试没有在成功前耗尽。否则「最终」无法由状态机单方面保证。

对安全协议、交易流程或高价值设备，可使用 TLA+/PlusCal、Promela/SPIN 或其他模型检查工具验证安全性、活性和无死锁性，同时通过有界、对称性约减与数据抽象控制状态空间。

## 11. 持久化、并发与分布式一致性

### 11.1 持久化边界

持久化内容可能不只是单一状态枚举，还包括：

- 扩展数据与不变量所需字段。
- 乐观并发版本。
- 活动的正交区域配置。
- 浅/深历史配置。
- 待恢复定时器的到期时间与 epoch。
- 已处理事件或业务幂等键。

恢复后必须重建与崩溃前等价的合法配置，而不是仅仅读回一个状态名。

### 11.2 乐观并发

多个工作节点可能同时基于版本 $v$ 计算转移。持久化更新应附带原版本条件：

```sql
UPDATE orders
SET state = @new_state,
    version = version + 1
WHERE id = @id
  AND version = @expected_version;
```

受影响行数为零时，应重新加载最新配置并重新执行业务判断，或向上游返回冲突。不能把旧转移结果直接覆盖到新状态上。

### 11.3 状态与效果的原子性

「状态已变更但消息未发送」和「消息已发送但状态事务回滚」都会破坏跨边界一致性。常见解法是事务性 Outbox：

1. 在同一数据库事务中保存新状态、版本和待发送效果。
2. 事务提交后由后台发布器读取 Outbox 并执行副作用。
3. 发布失败可重试；消费者使用事件 ID 或业务键幂等处理。

Outbox 通常提供至少一次（at-least-once）传递，不是端到端的恰好一次（exactly-once）。状态机必须对重复、乱序和过期事件有业务语义。

### 11.4 长时间流程

跨服务的长事务常用 Saga/Process Manager 编排；其内部可以是状态机，但还必须建模：

- 每一步的本地事务。
- 可重试的前向恢复。
- 不可继续时的补偿行为。
- 超时、人工介入和幂等。
- 允许临时存在的中间状态。

一张转移图本身不会让分布式流程变得原子。

## 12. 可观测性与模型演进

### 12.1 转移日志

每次事件处理至少应能关联以下字段：

| 字段                                       | 用途                         |
| ------------------------------------------ | ---------------------------- |
| MachineId / AggregateId                    | 标识具体机器实例             |
| EventId / CorrelationId                    | 去重与跨服务追踪             |
| Sequence / Version                         | 重建顺序、并发检测           |
| SourceState / TransitionName / TargetState | 说明选中路径                 |
| GuardResult                                | 诊断候选转移为何通过或被拒绝 |
| Effects                                    | 追踪外部副作用               |
| Duration / Outcome                         | 延迟、失败和重试监控         |

应区分「事件被忽略」、「无转移」、「守卫不通过」和「动作失败」，否则生产问题会被汇总成模糊的「状态机失败」。

### 12.2 运行指标

可按机器类型和状态监控：

- 转移数、拒绝数、幂等忽略数。
- 在各状态的停留时间分布。
- 事件队列深度、延迟与溢出。
- 超时、重试、补偿与人工介入数。
- 特定状态的异常积压，例如大量订单长时间停留在 `AwaitingPayment`。

实例 ID 通常是高基数标签，应记录在日志/追踪中，而不应直接作为时序数据库指标标签。

### 12.3 模型版本与迁移

状态机的拓扑会演进。上线前必须回答：

- 数据库中仍有旧状态名时如何加载。
- 删除或拆分状态时，现存实例如何迁移。
- 在途定时器和已发送旧事件使用哪个 Schema 版本。
- 新旧服务版本混合部署时，是否能同时理解持久化状态和消息。
- 回滚后新版本已产生的状态是否仍可读。

不应直接重命名已持久化的枚举文本并假设系统会自动兼容。

## 13. 常见错误

### 13.1 用多个布尔值隐式表达互斥状态

`IsPaid`、`IsCancelled`、`IsShipped` 三个独立可写布尔值能表达 $2^3=8$ 种组合，但其中很多组合在业务上非法。使用显式状态和转移方法可从表示层面缩小非法空间。

### 13.2 把所有数据组合展开为状态

地区、重试次数、支付方式、订单等级等独立维度的笛卡尔积会迅速造成状态爆炸。只有改变合法行为和生命周期语义的信息才应进入控制状态，其余作为扩展数据。

### 13.3 状态过少

将「等待支付结果」、「正在退款」、「等待人工审核」隐藏在临时字段中，会使超时、恢复和运维介入无法建模。若一个阶段需要独立的合法事件、时限或观测，它通常应是状态。

### 13.4 守卫具有副作用

如果守卫中读写数据库、调用网络、发布消息或修改模型，不同的候选顺序就会改变结果。守卫应基于已加载的事件和配置做纯判断，副作用只在转移被选中后产生。

### 13.5 动作内递归分派事件

这会破坏 RTC 的直观顺序，引入重入和栈溢出风险。应将新事件入队，在当前转移结束后再处理。

### 13.6 在 RTC 中执行长时间 I/O

同步等待支付、文件或网络会阻塞后续事件并模糊故障边界。应转移到「等待结果」状态，返回效果，再以异步结果事件继续推进。

### 13.7 忽略自转移与内部转移的区别

如果 `entry` 启动定时器或申请资源，错把外部自转移当成内部转移会导致重复执行或资源泄漏。测试应显式验证退出和进入次数。

### 13.8 取消定时器后假设超时事件不会到达

超时消息可能已在途中。事件应携带 attempt ID/epoch，由守卫拒绝过期结果。

### 13.9 将正交区域误解为多线程

状态图上的逻辑并发不等于实现必须并行。线程、调度、内存可见性和转移冲突是独立设计问题。

### 13.10 将 State Pattern 当作完整规格

为每个状态创建一个类不会自动给出转移完备性、事件队列、优先级和持久化语义。先定义模型和契约，再选择 State Pattern 作为代码组织方式。

### 13.11 图、代码与测试分别维护

当三者不共享可执行来源时，图通常会变成过期说明。可优先由转移表或模型文件生成图、覆盖清单和测试夹具。

## 14. 何时不应使用状态机

| 问题                                 | 更合适的方法                                 |
| ------------------------------------ | -------------------------------------------- |
| 无长期控制状态的纯数据变换           | 纯函数或普通服务                             |
| 大量独立规则需动态组合               | 规则引擎、决策表                             |
| 重点是令牌、资源同步与真并发流动     | Petri 网或专用并发模型                       |
| 简单 CRUD，没有状态相关业务规则      | 事务脚本或普通分层                           |
| 跨服务长事务                         | Saga/Process Manager；内部可使用持久化状态机 |
| 状态、数据和时间无法形成合理抽象边界 | 先重新划分领域或组件责任                     |

状态机是控制模型，不是通用业务规则容器。如果所有规则都被塞进守卫和动作，只是将「巨型服务」换成了「巨型状态机」。

## 15. 设计评审清单

### 15.1 模型与语义

- [ ] 状态机实例的边界、标识和初始状态是否明确？
- [ ] 状态是否代表持久行为阶段，扩展数据是否与控制状态区分？
- [ ] 事件与命令是否区分，事件载荷是否包含必要的 ID、时间和版本？
- [ ] 守卫是否无副作用，同一事件下的守卫是否互斥或有明确优先级？
- [ ] 每个相关状态—事件对是否明确为转移、忽略、延迟或拒绝？
- [ ] 自转移、内部转移、入口、退出和完成动作的语义是否已定义？
- [ ] 有层次/并发时，转移冲突、优先级与激活配置是否依据明确规范？

### 15.2 正确性与测试

- [ ] 不变量和必须禁止的状态/轨迹是否已写出？
- [ ] 是否检查了不可达状态、意外吸收状态、无事件环和守卫空洞？
- [ ] 每条转移和每个守卫真/假分支是否被测试？
- [ ] 重复、过期、乱序、未知、超时和故障事件是否有测试？
- [ ] 是否对关键事件序列做属性测试或模型驱动测试？
- [ ] 安全性和活性要求是否区分，活性的环境假设是否明确？

### 15.3 运行时与分布式机制

- [ ] 是同步直接调用还是事件队列，其顺序、容量、背压和重试契约是否明确？
- [ ] 是否避免递归分派和 RTC 中的长时间 I/O？
- [ ] 多线程或多节点更新是否有单消费者或乐观并发策略？
- [ ] 状态与待发送效果是否通过 Outbox 等机制建立原子边界？
- [ ] 消费者是否能幂等处理至少一次交付下的重复消息？
- [ ] 超时事件是否携带 attempt ID/epoch，以防止旧定时器污染新状态实例？
- [ ] 状态、扩展数据、历史配置和定时器是否可在崩溃后一致恢复？

### 15.4 运维与演进

- [ ] 日志是否包含机器 ID、事件 ID、源/目标状态、选中转移、版本和效果？
- [ ] 是否能监控状态停留时间、拒绝率、队列积压与超时？
- [ ] 状态图、代码和测试是否尽量来自同一规格？
- [ ] 持久化状态和事件 Schema 是否有版本、迁移、混合部署与回滚策略？

## 16. 术语速查

| 术语              | 定义                                             |
| ----------------- | ------------------------------------------------ |
| 控制状态          | 影响系统后续行为的离散阶段                       |
| 扩展状态          | 与控制状态共同决定转移的数据变量                 |
| 配置              | 控制状态/活动状态集与扩展数据的完整当前值        |
| 事件              | 已经发生、可能触发响应的事实                     |
| 触发器            | 使转移成为候选的事件或完成条件                   |
| 守卫              | 候选转移能否启用的无副作用布尔条件               |
| 转移效果          | 转移被选中后执行的动作                           |
| Run-to-completion | 当前事件的状态响应完成后才分派下一事件的原则     |
| 微步              | 一组互不冲突的转移选择及相关退出、效果与进入操作 |
| 宏步              | 由一个外部事件引发，直到机器重新稳定的一系列微步 |
| 复合状态          | 包含子状态的层次状态                             |
| 正交区域          | 在同一复合状态中逻辑并发激活的多个状态区域       |
| 浅/深历史         | 恢复上次直接子状态/完整嵌套激活配置的伪状态      |
| 终态              | 一个区域或机器已完成的状态                       |
| 状态爆炸          | 状态组合数随独立维度或并发区域乘法增长的现象     |
