# 开源协议（Open Source License）

开源协议规定了他人使用、修改和分发软件时享有的权利，以及必须履行的义务。对开发者而言，最常见的问题是：这段代码能否用于自己的产品，修改后是否需要提供源码，发布时应保留哪些声明。

理解常见协议，可以先抓住一个区别：**宽松协议通常允许闭源使用；Copyleft 协议要求在特定情况下，继续开放受其约束的代码。** 具体范围可能是文件、库或组合作品，并不总是整个项目。

## 1. 先分清几个概念

**开源不等于免费。** 开源软件允许商业使用，可以用于企业业务，也可以收费销售。需要区分的是“能否商用”和“能否作为闭源产品分发”：GPL 允许商用，但对受其覆盖的作品有源码提供和许可要求。

**源码公开不等于获得授权。** 软件通常自动受著作权保护。仓库能被浏览、下载或 fork，不代表可以任意复制、修改并用于产品。应查找 `LICENSE`、`COPYING`、文件头或其他许可声明；找不到明确授权时，应先确认来源和使用权限。

**Copyleft 不意味着任何关联代码都必须开源。** 它通过许可条件保留接收者修改和再分发软件的自由。MPL 主要约束受覆盖的文件，LGPL 关注库及其使用方式，GPL 则可能约束基于原程序形成的整个作品。独立程序只是一起打包，并不当然适用同一许可证。

还应区分“开源”与“源码可得”。限制商业用途或特定服务方式的许可证，未必符合 [OSI 的开源定义](https://opensource.org/osd)。例如 SSPL 和 Business Source License 1.1（`BUSL-1.1`）不能按普通开源协议理解；后者也不要与开源的 Boost Software License（`BSL-1.0`）混淆。

## 2. 常见协议对照

下表中的协议都允许商业使用，重点区别在于**闭源组合和分发时的条件**。“提供源码”通常面向软件接收者，AGPL 的特定情形还包括远程交互用户，不一律等于公开整个代码仓库。

| 协议 | 能否用于闭源产品 | 源码要求 | 其他主要要求 |
| --- | --- | --- | --- |
| MIT | 可以 | 不要求公开修改 | 保留版权与许可声明 |
| BSD-2-Clause / BSD-3-Clause | 可以 | 不要求公开修改 | 保留规定声明；三条款版另有非背书要求 |
| Apache-2.0 | 可以 | 不要求公开修改 | 保留许可及相关声明，标明修改，处理上游 NOTICE；含明示专利许可 |
| MPL-2.0 | 可以与独立的闭源文件组合 | 分发时使受 MPL 覆盖文件的源码可获得 | 覆盖文件继续按 MPL 提供 |
| LGPL | 满足条件时可以 | 随产品交付库时，须提供其相应源码 | 保障用户修改库并替换或重新链接的能力 |
| GPL | 受其覆盖的组合作品通常不能整体闭源分发 | 分发时提供相应作品的对应源码 | 相关作品按 GPL 提供 |
| AGPL | 受其覆盖的组合作品通常不能整体闭源分发 | 除分发要求外，特定修改版须向网络交互用户提供源码获取机会 | 在 GPL 类规则上增加网络交互要求 |

表格用于初步筛选。实际判断仍须确认协议版本、例外条款、代码组合方式和交付内容。

## 3. 主要协议的使用要点

### 3.1 MIT 与 BSD：保留声明，允许闭源使用

MIT 允许使用、复制、修改、再分发和销售软件，也允许将代码纳入闭源产品。主要条件是在软件副本或实质性部分中保留版权与许可声明。实际发布时，通常将完整文本放入第三方许可文件。

BSD 与 MIT 的使用方式相近，但要看具体版本。两条款版要求在源码或二进制的随附材料中保留规定声明；三条款版还规定，未经许可，不得使用原作者或贡献者的名称为派生产品背书。

例如，商业应用使用 MIT 库，无须因此公开自己的业务代码，但仍需随产品保留相应声明。**允许闭源，不等于可以删除原作者的署名和许可条件。**

### 3.2 Apache-2.0：增加专利与声明安排

Apache-2.0 同样允许闭源和商业使用，发布时主要注意四件事：

1. 向接收者提供许可证副本。
2. 在修改过的文件中显著说明修改。
3. 保留仍适用的版权、专利、商标和署名声明。
4. 上游含有 `NOTICE` 时，按规定传递其中仍相关的署名信息。

上游没有 NOTICE 时，不必仅因采用 Apache-2.0 就凭空创建一份。NOTICE 也不能代替 LICENSE。

Apache-2.0 还提供明确的贡献者专利许可，但只覆盖条款规定的相关专利权利要求，并非所有专利的全面授权。针对作品提起条款所述的专利诉讼，可能导致相应专利许可终止。

### 3.3 MPL-2.0：保持受覆盖文件开放

MPL-2.0 以文件为主要边界。修改 MPL 文件，或者把其中的代码复制进新文件，相关文件仍可能受 MPL 约束；与这些文件分立、没有包含 MPL 代码的文件，可以使用其他许可，包括闭源许可。

分发可执行程序时，需要让接收者能够取得受覆盖部分的源码，并告知获取方式。即使没有修改原组件，也不能省略这一要求。

因此，MPL 适合希望核心文件保持开放、同时允许它们与商业代码组合的项目。

### 3.4 LGPL：允许闭源应用使用库，但要保留修改能力

LGPL 常用于软件库。应用在满足条件时可以保持闭源，但库本身及其修改仍应按相应许可处理，用户需要能够使用修改后的库。应用条款也不能禁止为调试这些修改而进行的反向工程。

动态链接是常见实现方式，但“使用 DLL”不代表自动合规：如果程序只能加载厂商签名的原版库，就需要进一步检查。静态链接也不是一律禁止，通常可以通过提供应用目标文件等材料，让用户与修改后的库重新链接。

还要区分库由谁提供。应用仅调用用户系统已有的库，与自己随安装包分发库，是不同情况；后者仍须履行库源码提供义务。LGPL-2.1 与 LGPL-3.0 的具体要求不同，采用 v3 的组合作品还应随附 GPLv3 和 LGPLv3 两份文本。

### 3.5 GPL：分发相关作品时保留源码与使用自由

GPL 允许运行、修改和收费分发软件。其核心要求是：向他人分发基于 GPL 程序形成的受覆盖作品时，应按 GPL 提供相关作品，并按规定提供对应源码。

这里的对应源码应与实际交付版本匹配，包括必要的修改和构建脚本，不能用未经修改的上游仓库链接代替。不同分发方式允许采用不同的源码提供方案，选择书面要约时还要满足其期限等条件。

GPL 通常不要求公开未分发的私人修改版。单纯在服务器运行 GPL 程序、没有向用户交付副本，也通常不会触发这一分发义务。不过，安装包、客户镜像和浏览器端代码都可能涉及副本交付。

不能仅用“动态链接”或“另起一个进程”判断是否受 GPL 覆盖。应结合实际代码关系、接口和适用条款分析；独立程序的单纯聚合与形成一个组合作品，需要分别处理。

### 3.6 AGPL：关注修改版的网络服务

AGPLv3 在 GPL 类规则之外增加了网络交互要求。第 13 条规定：修改后的程序若支持远程网络交互，应显著地向所有通过网络与该修改版交互的用户提供免费取得对应源码的机会。

例如，修改一个 AGPL Web 应用后向用户提供服务，不能因为“没有分发安装包”就省略源码入口。源码应包含实际运行版本的相关修改，而不是仅提供上游原版。

这一规则并没有把网络使用定义为分发，也不意味着服务器上出现一个 AGPL 组件，整个业务系统就自动适用 AGPL。仍需判断修改、交互和作品范围；“部署在内网”本身也不能排除该条款。

## 4. 如何选择协议

为自己的项目选证，可以先考虑希望下游如何使用它。

| 主要目标 | 优先考虑 |
| --- | --- |
| 希望广泛采用，允许下游闭源使用 | MIT 或 BSD |
| 允许广泛使用，并希望明确贡献者专利许可 | Apache-2.0 |
| 希望受覆盖的源文件持续开放 | MPL-2.0 |
| 希望库保持开放，同时允许闭源应用使用 | LGPL |
| 希望分发后的相关作品继续按相同自由传播 | GPL |
| 希望修改版提供网络服务时也向用户提供源码 | AGPL |

如果只是发布通用工具或小型库，MIT 通常容易理解和采用；如果重视明确的专利安排，可以考虑 Apache-2.0。希望下游持续提供相应源码时，再根据文件、库或作品的范围选择 Copyleft 协议。

**选择自己的协议之前，先检查已经引入的代码。** 新增一份 LICENSE 不能改变第三方代码的授权。几个常见的兼容性问题值得记住：

- MIT、两条款和三条款 BSD 代码通常可以纳入 GPL 作品，但原有声明仍须保留。
- Apache-2.0 与 GPLv3 有兼容路径，与 `GPL-2.0-only` 不兼容。
- `GPL-2.0-only` 与 `GPL-3.0-only` 不能直接按标准许可组合分发；前者若是 `GPL-2.0-or-later`，则可以选择 GPLv3 路径。

这些结论针对需要共同履行许可的组合作品。独立程序的聚合、附加例外或另行商业授权，可能改变判断。

## 5. 引入依赖与发布项目

### 引入第三方代码

日常开发可以按四步处理：

1. **确认来源和版本。** 查看实际使用版本的许可文件，检查传递依赖、复制片段和素材，不只看项目首页的协议标签。
2. **确认使用方式。** 区分内部运行、修改、随产品分发和提供网络服务，判断哪些代码受到约束。
3. **准备所需材料。** 保留许可、署名和相关 NOTICE；存在源码、替换或重链接要求时，准备对应材料。
4. **在发布时核对。** 确保声明进入最终安装包或镜像，源码与二进制版本一致，获取入口可用。

商业应用通常会设置“开源软件声明”页面，并随产品附带 `THIRD-PARTY-NOTICES` 或 `licenses/` 目录。文件名称可以自行安排，内容和交付方式应满足各组件的要求。

### 发布自己的项目

先确认自己有权许可相关代码，再在仓库中放置完整许可证文本，并在 README 说明适用范围。包含第三方代码时，应继续保留它们的原有许可和声明。

包元数据宜使用 SPDX 标准标识，例如 `MIT`、`Apache-2.0`、`GPL-3.0-only`。几个表达式的区别如下：

| 写法 | 含义 |
| --- | --- |
| `GPL-3.0-only` | 仅允许按 GPLv3 使用 |
| `GPL-3.0-or-later` | 可选择 GPLv3 或后续版本 |
| `MIT OR Apache-2.0` | 使用者可以择一遵守 |
| `MIT AND BSD-3-Clause` | 两套条件均需要满足 |
| `GPL-2.0-only WITH Classpath-exception-2.0` | 按 GPLv2 及指定例外共同判断 |

元数据应描述真实授权，不能自行把多个第三方许可证写成可任意选择的 `OR`。项目规模较大时，可以用扫描工具和 SBOM（软件物料清单）记录依赖，但工具结果仍需与实际文件和发行物核对。

## 6. 常见问题

**修改后必须向原项目提交代码吗？**

一般不要求。Copyleft 的源码义务通常面向软件接收者或符合条件的网络交互用户，不等于必须向上游提交 PR。

**只复制几行代码，可以忽略协议吗？**

不能仅按行数判断。要看内容是否属于受保护的表达以及原有授权；无法确认时，保留来源并核实许可。

**用了 GPL 编译器，编译出来的程序也必须用 GPL 吗？**

不会仅因使用该工具而如此。若输出中包含工具、模板或运行库的代码，则需另查这些材料及其例外授权。

**开源组件的名称和标志可以直接用于宣传吗？**

软件许可不等于商标授权。说明组件来源与宣称原作者为自己的产品背书，是不同的行为。

**以后能换协议吗？**

可以评估，但前提是拥有相应权利。第三方代码和外部贡献可能限制重新许可；项目换证也不会自动撤销接收者已合法取得的旧版本许可。
